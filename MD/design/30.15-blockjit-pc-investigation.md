## What we wanted

Run `apr-pc --bios=pcxtbios.bin --floppy-a=freedos-1.3.img --backend=json-block`
and have FreeDOS boot to `A:\>` — same as `--backend=json` does today.
This would unlock the biggest interactive-speed win for the PC harness
(json-block was measured ~7.5× faster than json on isolated FPU
integration test, per Phase 30.15 smoke run).

## Symptom

- POST runs ("Turbo XT BIOS v2.5", "Testing RAM: 600K OK", FPU detected).
- VBIOS init runs (Tseng ET4000 option-ROM `caller=C000` appears in trace
  157 times) and switches mode to 3 (CGA colour text).
- pcxtbios INT 19h transfers control to boot sector at 0:7C00.
- FreeDOS boot sector executes correctly:
  - `EB 3C` JMP, `FA FC 31 C0` CLI/CLD/XOR AX,AX init
  - `F3 A5` REP MOVSW relocates 256 words from 0:7C00 to 1FE0:7C00
  - `EA 5E 7C E0 1F` JMP far 1FE0:7C5E (the relocated copy)
  - 1FE0:7C5E `8E D8 8E D0` MOV DS, AX; MOV SS, AX (AX=1FE0)
- **Some unknown number of instructions later, CPU is at 1FE0:???0F
  with bytes `00 00 00 00`** (the "zero sled" — Gemini consult
  20260517_024459.txt Q2 analysis).
- PIT IRQ 0 keeps firing; IRET returns to the next 0x180-bytes-later
  zero address; CPU drifts through uninitialised FreeDOS kernel area
  forever, never executing actual kernel code, never producing screen
  output.

Per-instr path at the same point (5M architectural instructions in)
reaches the FreeDOS install welcome screen in full colour.

## What we ruled OUT

| Hypothesis | Test | Result |
|---|---|---|
| **SMC cache invalidation failure (Gemini hypothesis #1)** | Added `X86JsonCpu._activeCpu` static + `NotifyExternalMemoryWrite` static hook. Wired `MemWrite8` extern + `Fdc8272.ReadDataExecute` DMA loop to call `BlockCache.NotifyMemoryWrite(addr)` per byte. | **NO fix**. Symptom unchanged. (Fix still landed as cleanup — it WAS a real bug, just not the one causing the divergence.) |
| **Intra-block LLVM optimisation (mem2reg / GVN reordering)** | `APR_X86_BLOCK_MAX=1` env var forces block size to one instruction = effectively per-instr through the JIT compiler, defeating all multi-instruction optimisations. | **NO fix**. Black screen, identical symptom. Rules out intra-block reordering. |
| **`MOV SS` / IRQ-window violation (Gemini hypothesis #3)** | Added `APR_DISABLE_PIT_IRQ` env var that skips `Pic8259.AssertIrq(0)` from `PcPit`. Diagnostic-only; reverted from the committed code. | **NO fix**. Black screen even with PIT IRQ never firing. Rules out IRQ timing. |

## What we still suspect

Gemini consult 20260517_024459.txt narrowed it to two remaining classes
after block-size=1 ruled out intra-block bugs:

- **Memory aliasing across the C# extern boundary**. Per-instr CPU
  reads/writes go directly through `X86Memory.ReadByte`/`WriteByte` in
  managed C#. Block-JIT goes through the unmanaged `MemRead8`/`MemWrite8`
  externs (declared `[UnmanagedCallersOnly]`). If the JIT-emitted IR
  treats two consecutive memory ops as not aliasing (no TBAA / volatile
  metadata) and LLVM reorders or caches them, observable behaviour
  diverges from per-instr's strict-order managed loop.
- **Lazy EFLAGS calculation diverging in some specific opcode**.
  Block-JIT may defer flag computation while per-instr always commits
  it. A `CMP` / `TEST` / shift inside the FreeDOS kernel-load code path
  could produce the wrong condition under block-JIT, taking the wrong
  branch and ending in the zero-sled.

Both require an instruction-by-instruction lockstep diff against per-instr
to pinpoint the first divergent state. Quick screen-scrape comparisons
won't be enough — the divergent instruction is buried among millions of
correct ones.

## Recommended next-sprint plan

1. **Wire `LockstepDiff` to x86** — `src/AprCpu.Core/Validation/LockstepDiff.cs`
   already provides the generic harness via `ISteppableCpu`. Wrap two
   `X86JsonCpu` instances (one with `enableBlockJit=false`, one with
   `=true`), share memory carefully (one of them needs a memory-mirror
   so writes don't interfere), step both forward, assert AX..DI + FLAGS
   + DS/ES/SS/CS:IP match at each architectural-instruction boundary.
2. **Quirk**: under block-JIT each Step() executes a whole block. Lockstep
   needs to:
   - Capture next-block address from JIT's compiled IR (BlockDetector
     already returns the block's instruction list).
   - Step per-instr CPU forward exactly N instructions to match.
3. **Disable interrupts** during the diff so PIT/FDC don't fire at
   different points in the two runs (Gemini hypothesis: false-positive
   divergences). Force-mask IRQs via the PIC IMR at startup or via the
   `APR_DISABLE_PIT_IRQ` env var (re-add after this commit if useful).
4. **Bisect on block start address**. Once divergence found, dump the
   LLVM IR for that specific block (`APR_LLVM_IR_DUMP=ADDR` env var) and
   inspect the load/store ordering, TBAA metadata, alloca shadow
   semantics for that block's specific opcode mix.

Estimated effort: 3-5 days.

## Phase 30.15b update (2026-05-17) — **FIRST BLOCK-JIT BUG FOUND AND FIXED**

Built the LockstepDiff x86 wiring described in the previous sprint
plan. Ran `apr-pc --lockstep-bjit` against pcxtbios.bin + freedos-1.3
boot. **First divergence at step 25282**: instruction `8B 17` (MOV DX,
[BX]) at CS=0x30:IP=0xF6 (linear 0x3F6).
- Per-instr: IP 0xF6 → 0xF8 (+2, correct)
- Block-JIT: IP 0xF6 → **0x3F8** (+0x302, wrong)

Root cause: `BlockFunctionBuilder.cs` line ~317 pre-wrote PC slot as
`(bi.Pc + 1) & widthMask`, where `bi.Pc` is the LINEAR 20-bit address
(CS<<4)+IP for x86. The mask & 0xFFFF accidentally produced the right
value when CS=F000 (linear 0xFExxx & 0xFFFF = original IP), so all
BIOS-resident code paths silently worked. But for CS=0x30:IP<0x200
(scratch area FreeDOS boot uses), linear-masked-to-16-bits != real IP,
and the IP slot got `linear + 1` instead of `IP + 1`. Next memory
fetch read from wrong address → wild execution → zero-sled.

Fix: replaced the static `(bi.Pc + 1)` with `IP_at_block_entry +
(bi.Pc - blockStartLinear) + 1`, computed at runtime by loading the
IP slot once at block entry. Works regardless of (CS, IP) the caller
used to reach the cached block.

Validation:
- `--lockstep-bjit --max-cycles=5000000` with VBIOS + deterministic
  PIT tick (200 instr/tick, no IRQ assertion) → 5M steps NoDiff. Took
  37 seconds.
- Pre-fix reproduced divergence at step 25282 every time.
- 227/227 X86 unit tests still pass.

## Phase 30.15c-1 (2026-05-17) — second divergence located, NOT IRQ-path

Added `APR_LOCKSTEP_IRQ=1` mode to the lockstep harness:
`X86LockstepStepper.Step()` now mirrors PcSystemRunner's pre-step
IRQ-delivery shape (synthesise PUSH FLAGS/CS/IP + JMP IVT[n]) and the
deterministic-PIT tick now also asserts IRQ 0. With IRQ delivery
turned on, lockstep diverges at step **356358** (vs 5M+ NoDiff without
IRQ).

Divergence shape:
```
i=356358 (matched)  C4 5E C4   LES BX, [BP+0xC4]   SS:7CC4 → ES:BX
  A: BX = 0x63A0  (memory at 0x27CC4 contained 0x63A0)
  B: BX = 0x0000  (memory at 0x27CC4 contained 0x0000)
Both ES → 0x1FE0
```

Both CPUs read the SAME memory address (1FE0:7CC4 = phys 0x27CC4) but
got DIFFERENT values. CPU register state matched up to this point.
**Therefore the memories had silently diverged earlier and only
surfaced when an instruction happened to read the diverged byte.**

This is NOT an IRQ-delivery bug per se — IRQ delivery just enabled the
boot to progress far enough that the EARLIER block-JIT memory-write
bug to surface. The actual bug is in some memory-write instruction
(or chain of them) that produces different memory contents between
per-instr and block-JIT, even at architecturally-identical step
counts.

## Phase 30.15c-2 (next) — extend lockstep to compare memory

To find the FIRST diverging memory byte, the harness needs to compare
memory state in addition to CPU state. Options:
- **Cheap**: per-step hash (e.g. 64-bit xxhash of all 1 MB RAM).
  Hash mismatch → diverged. Doesn't tell us WHICH byte without a
  bisect step (snapshot at midpoint, compare halves).
- **Medium**: byte-by-byte compare every K steps (K = 1000 or so).
  Slow but precise — reports first mismatching address.
- **Expensive**: byte-by-byte at EVERY step. Best precision, ~5×
  slowdown — but acceptable for this hunt.

Cheap-then-medium is the right combo: snap a hash every step, if
mismatch then re-run with byte-compare to localise the exact byte
and step.

## Phase 30.15c (open) — async IRQ delivery still broken

Even with the IP-prewrite bug fixed, normal headless `--backend=
json-block --bios=pcxtbios.bin` real-BIOS boot **still hangs to a
black screen**. Both `APR_X86_BLOCK_MAX=1` (single-instr blocks) AND
default block size produce the same hang. PIT IRQ ENABLED is the
trigger — lockstep with PIT disabled runs perfectly.

This narrows the second bug to **asynchronous IRQ delivery between
block boundaries**. `PcSystemRunner.EmulatorThreadProc` calls
`_pic.DequeueNextVector() → DeliverInterrupt → _cpu.LoadState(st)`
between `_cpu.Step()` calls. Under block-JIT the state-buffer save
/restore around blocks may be missing some register or interleaving
with the IRQ-delivery state save/restore incorrectly.

Hypotheses (not yet tested):
- The block-JIT shadow allocas for GPRs / status regs are not drained
  back to the state buffer **between blocks** if a block exits via
  the per-instruction advance path that DOESN'T set PcWritten.
  Solution: ensure shadow drain at every block exit, not just the
  "ret void" final branch.
- `_cpu.LoadState(st)` writes the state buffer but block-JIT's
  shadow allocas re-init from buffer values only AT BLOCK ENTRY.
  Between block exit and entry, anything that mutates state buffer
  is consistent. But INTRA-block IRQ delivery wouldn't be allowed —
  CPU instructions on guest can flip CLI/STI mid-block and host
  IRQ delivery has to wait for block exit. The block-exit check
  uses post-block IF, which might miss a transient IF=1 window the
  per-instr backend would have honored.

Diagnostic next step: extend `--lockstep-bjit` to re-enable the
PIT timer (or manually inject IRQs every N steps via direct
`_pic.AssertIrq(0)` + force IRQ delivery in stepper). Find first
divergence; that'll point at the wrong-IRQ-window code.

## Phase 30.15d sprint 5.4b/5.4c — verifier framework correctness fixes

After the framework's sprint 5.1-5.4 landed, two bugs in the VERIFIER
ITSELF (not in the JIT under test) caused false-positive divergences
that masked the real CPU-emitter bug. Both fixed here:

1. **HW-state desync (5.4b)** — PcPortBus has cycling counters (CGA
   status port `0x3DA` returns inverted-pulse `0x09/0x01` every call;
   kbd FIFO advances on every read). The JIT env and INTERP env each
   advanced their counters independently, so by block #39,836 the
   mem-write traces differed for any code that latched a port value
   into RAM. Fix: snapshot PortBus state from the JIT env at block
   entry, restore into INTERP env before its verification pass.
   Wired via new `X86SteppableCpu.AdditionalSnapshot/Restore` hooks +
   `PcPortBus.Snapshot()` blob.
2. **JIT actual instr count (5.4c)** — `entry.InstructionCount` is the
   COMPILE-TIME block size from `BlockDetector.Detect`. A block of 59
   detected instructions may execute only the first 3 if instr #3 is
   a taken Jcc/RET. The verifier was driving the INTERP side for the
   detected count (59), so for any block with an early-exit branch
   the two CPUs ran wildly different instruction lists. Fix: new
   `LastInstrIndexFieldIndex` (i32) state slot; `BlockFunctionBuilder`
   writes `(i+1)` at the start of each instruction's preBB; host reads
   it post-call to get the actual completed count.
3. **Stale `LastBlockInstructionCount` (5.4c sub-fix)** — When
   `Step()` fell through to per-instr (prefix byte case, or block
   compile bailed), the variable held the prior block's value (e.g.
   59). Fix: `Step()` per-instr fall-through path explicitly sets
   `LastBlockInstructionCount = 1`.

Result: verifier framework progresses from divergence at block #2
(false positive) → block #19,471 (false positive — INTERP read JIT
env's PortBus) → **1,000,000 blocks verified OK with NoDiff** after
sprint 5.4d (`OnBeforeStep` hook switches `PcPortBus.Active`
between envs per step).

This means: under PIT-disabled lockstep conditions, the x86-16
block-JIT emitter produces architecturally-identical state +
mem-write trace + side-effect log as the per-instruction interpreter
for **4.38 million consecutive architectural instructions of real
pcxtbios + FreeDOS boot code** with zero divergences. The three real
CPU bugs (Phase 30.15b/c-B/c-C) found earlier with the prototype
verifier are now confirmed comprehensively fixed.
