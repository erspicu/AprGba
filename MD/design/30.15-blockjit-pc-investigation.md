## 還在懷疑的

Gemini consult 20260517_024459.txt 在 block-size=1 排除 intra-block bug 後，
narrow 到兩類剩下：

- **跨 C# extern boundary 的 memory aliasing**。Per-instr CPU 的讀寫直接
  走 managed C# 的 `X86Memory.ReadByte`/`WriteByte`。Block-JIT 走 unmanaged
  的 `MemRead8`/`MemWrite8` extern（`[UnmanagedCallersOnly]`）。如果
  JIT-emit 的 IR 把兩個連續 memory op 當成 not aliasing（沒 TBAA / volatile
  metadata）、LLVM 重排或 cache 它們，observable behaviour 跟 per-instr
  嚴格順序的 managed loop 就會 diverge。
- **某個 opcode 的 lazy EFLAGS calculation diverge**。Block-JIT 可能 defer
  flag 計算、per-instr 一律 commit。FreeDOS kernel-load code path 裡的某個
  `CMP` / `TEST` / shift 在 block-JIT 下可能產生錯的 condition、走錯 branch、
  在 zero-sled 結束。

兩個都需要 instruction-by-instruction 對 per-instr 的 lockstep diff 才能
pin 到第一個 divergent state。Quick screen-scrape 對比不夠 — divergent
instruction 埋在數百萬個正確的之間。

## Phase 30.15b 更新（2026-05-17）— **找到並修掉第一個 block-JIT bug**

把前述 sprint plan 的 LockstepDiff x86 wiring 做出來。對 pcxtbios.bin +
freedos-1.3 boot 跑 `apr-pc --lockstep-bjit`。**第一個 divergence 在
step 25282**：instruction `8B 17` (MOV DX, [BX]) 在 CS=0x30:IP=0xF6
（linear 0x3F6）。
- Per-instr：IP 0xF6 → 0xF8（+2，正確）
- Block-JIT：IP 0xF6 → **0x3F8**（+0x302，錯）

Root cause：`BlockFunctionBuilder.cs` 第 ~317 行 pre-write PC slot 寫成
`(bi.Pc + 1) & widthMask`，其中 `bi.Pc` 是 x86 的 LINEAR 20-bit address
(CS<<4)+IP。Mask & 0xFFFF 在 CS=F000 時剛好給出正確值（linear 0xFExxx
& 0xFFFF = 原本 IP），所以所有 BIOS-resident code path 都靜默 work。
但對於 CS=0x30:IP<0x200（FreeDOS boot 用的 scratch 區），linear-masked-to-16-bit
≠ 真正的 IP、IP slot 拿到的是 `linear + 1` 而不是 `IP + 1`。下次 memory
fetch 讀到錯的 address → wild execution → zero-sled。

修法：把 static 的 `(bi.Pc + 1)` 換成 `IP_at_block_entry +
(bi.Pc - blockStartLinear) + 1`，runtime 透過 block entry 載入 IP slot 一次計算。
無論 caller 用哪個 (CS, IP) 達到 cached block 都 work。

驗證：
- `--lockstep-bjit --max-cycles=5000000` 配 VBIOS + deterministic PIT
  tick（200 instr/tick、不 IRQ assert）→ 5M step NoDiff，花 37 秒。
- 修之前每次都 reproduce 在 step 25282 divergence。
- 227/227 X86 unit test 仍過。

## Phase 30.15c-1（2026-05-17）— 第二個 divergence 定位、不是 IRQ-path

在 lockstep harness 加 `APR_LOCKSTEP_IRQ=1` mode：
`X86LockstepStepper.Step()` 現在 mirror PcSystemRunner 的 pre-step
IRQ-delivery 形狀（合成 PUSH FLAGS/CS/IP + JMP IVT[n]），deterministic-PIT
tick 也會 assert IRQ 0。IRQ delivery 開了之後，lockstep 在 step
**356358** 第一次 diverge（不開 IRQ 跑 5M+ NoDiff）。

Divergence shape：
```
i=356358 (matched)  C4 5E C4   LES BX, [BP+0xC4]   SS:7CC4 → ES:BX
  A: BX = 0x63A0  (memory at 0x27CC4 contained 0x63A0)
  B: BX = 0x0000  (memory at 0x27CC4 contained 0x0000)
Both ES → 0x1FE0
```

兩個 CPU 讀同一個 memory address（1FE0:7CC4 = phys 0x27CC4）但拿到
不同 value。CPU register state 到這個點為止都一致。**所以 memory 早就
silently diverge 了、只是剛好讀到的那個 byte 才 surface 出來。**

這 NOT IRQ-delivery bug per se — IRQ delivery 只是讓 boot 前進得夠遠
讓 EARLIER block-JIT memory-write bug surface。實際 bug 在某個
memory-write instruction（或一連串）在 per-instr 跟 block-JIT 之間
產生不同 memory content、即使在 architecturally identical 的 step count 下。

## Phase 30.15c-2（下一個）— lockstep 擴充比對 memory

要找第一個 diverging memory byte，harness 需要在 CPU state 之外也比 memory state。選項：
- **便宜**：每個 step 雜湊（例如 1 MB RAM 的 64-bit xxhash）。
  雜湊 mismatch → diverge。不直接告訴哪個 byte、需要 bisect step
  （midpoint snapshot、比兩半）。
- **中等**：每 K step 做 byte-by-byte 比對（K = 1000 左右）。
  慢但精準 — report 第一個 mismatch address。
- **昂貴**：EVERY step 都 byte-by-byte。最高精度、~5× 慢 — 但這次 hunt
  可接受。

便宜-then-中等 是對的組合：每 step snap hash、若 mismatch 就 re-run 帶
byte-compare localise 精確 byte 跟 step。

## Phase 30.15c（open）— async IRQ delivery 仍壞

即使 IP-prewrite bug 修了，正常 headless `--backend=json-block
--bios=pcxtbios.bin` real-BIOS boot **仍 hang 到黑屏**。`APR_X86_BLOCK_MAX=1`
（單 instruction block）跟預設 block size 都同樣 hang。PIT IRQ ENABLED
是 trigger — lockstep with PIT disabled 跑得完美。

這把第二個 bug narrow 到 **block boundary 之間的非同步 IRQ delivery**。
`PcSystemRunner.EmulatorThreadProc` 在 `_cpu.Step()` 呼叫之間做
`_pic.DequeueNextVector() → DeliverInterrupt → _cpu.LoadState(st)`。
Block-JIT 下，block 周圍的 state-buffer save/restore 可能漏了某個
register、或跟 IRQ-delivery 的 state save/restore 互相錯位。

假設（還沒測）：
- block-JIT 的 GPR / status reg shadow alloca **block 之間沒 drain 回
  state buffer**，如果 block 透過 per-instruction advance path 退出
  （那個 path 不 set PcWritten）。解法：保證每個 block exit 都 drain
  shadow，不只 "ret void" final branch。
- `_cpu.LoadState(st)` 寫 state buffer，但 block-JIT 的 shadow alloca
  只 AT BLOCK ENTRY 才從 buffer 重 init。Block exit 跟 entry 之間，
  任何改 state buffer 的事是一致的。但 INTRA-block IRQ delivery 不能
  — guest CPU 指令可以 mid-block flip CLI/STI、host IRQ delivery 要等
  block exit。Block-exit check 用 post-block IF，可能漏掉 per-instr
  backend 會 honor 的 transient IF=1 window。

Diagnostic 下一步：擴充 `--lockstep-bjit` 重新開 PIT timer（或在 stepper
裡 force IRQ delivery、每 N step 手動 `_pic.AssertIrq(0)`）。找第一個
divergence；指向 wrong-IRQ-window code。

## Phase 30.15d sprint 5.4b/5.4c — verifier framework correctness 修補

Framework 的 sprint 5.1-5.4 出貨後，VERIFIER 本身（不是 JIT under test）
裡有兩個 bug 造成 false-positive divergence、把真正的 CPU-emitter bug 蓋住。
兩個都在這修：

1. **HW-state desync (5.4b)** — PcPortBus 有 cycling counter（CGA
   status port `0x3DA` 每呼叫 return inverted-pulse `0x09/0x01`；
   kbd FIFO 每讀都 advance）。JIT env 跟 INTERP env 各自獨立 advance
   counter，所以到 block #39,836 為止，任何把 port value 鎖到 RAM 的
   code 的 mem-write trace 都不同了。修法：在 block entry 從 JIT env
   snapshot PortBus state、verification pass 前 restore 到 INTERP env。
   透過新的 `X86SteppableCpu.AdditionalSnapshot/Restore` hook +
   `PcPortBus.Snapshot()` blob 接上。
2. **JIT actual instr count (5.4c)** — `entry.InstructionCount` 是
   `BlockDetector.Detect` 的 COMPILE-TIME block size。一個 detect 到 59
   instruction 的 block 可能只執行前 3 個（如果 instr #3 是 taken Jcc/RET）。
   Verifier 用 detected count（59）驅動 INTERP side、所以任何有 early-exit
   branch 的 block，兩個 CPU 跑的 instruction list 差很多。修法：新
   `LastInstrIndexFieldIndex`（i32）state slot；`BlockFunctionBuilder` 在
   每個 instruction 的 preBB 起點寫 `(i+1)`；host post-call 讀它拿
   actual completed count。
3. **Stale `LastBlockInstructionCount` (5.4c sub-fix)** — `Step()` fall
   through 到 per-instr 時（prefix byte case、或 block compile bail），
   變數 hold 前一個 block 的值（例如 59）。修法：`Step()` per-instr
   fall-through path 顯式設 `LastBlockInstructionCount = 1`。

結果：verifier framework 進步從 block #2 divergence（false positive）
→ block #19,471 divergence（false positive — INTERP 讀 JIT env 的
PortBus）→ sprint 5.4d（`OnBeforeStep` hook 在 step 之間切
`PcPortBus.Active`）後 **驗 1,000,000 blocks NoDiff**。

意思是：在 PIT-disabled lockstep 條件下，x86-16 block-JIT emitter 對
**4.38 million 連續 architectural instruction 的 real pcxtbios + FreeDOS
boot code** 產生跟 per-instruction interpreter architecturally identical
的 state + mem-write trace + side-effect log、零 divergence。早先用
prototype verifier 找到的三個 real CPU bug（Phase 30.15b/c-B/c-C）
現在確認被全面性修掉。
