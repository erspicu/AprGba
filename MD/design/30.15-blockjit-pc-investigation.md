# Phase 30.15 — Block-JIT real-BIOS divergence investigation

> **Status**: 🔍 investigation only — **SMC cache fix landed** (the one
> bug we cracked), **root cause of remaining symptom still open**.
> Block-JIT on real pcxtbios + FreeDOS hangs after POST and never
> reaches an interactive prompt. Per-instr path works fully. Reserve
> a dedicated multi-day sprint to follow the diagnostic plan below.

## What we wanted

Run `apr-pc --bios=pcxtbios.bin --floppy-a=freedos-1.3.img --backend=json-block`
and have FreeDOS boot to `A:\>` — same as `--backend=json` does today.
This would unlock the biggest interactive-speed win for the PC harness
(json-block was measured ~7.5× faster than json on isolated FPU
integration test, per Phase 30.15 smoke run).

## Symptom

- POST runs ("Turbo XT BIOS v2.5", "Testing RAM: 600K OK", FPU detected).
- VBIOS init runs (Tseng ET4000 option-ROM `caller=C000` appears in trace
  157 times) and switches mode to 3 (CGA colour text).
- pcxtbios INT 19h transfers control to boot sector at 0:7C00.
- FreeDOS boot sector executes correctly:
  - `EB 3C` JMP, `FA FC 31 C0` CLI/CLD/XOR AX,AX init
  - `F3 A5` REP MOVSW relocates 256 words from 0:7C00 to 1FE0:7C00
  - `EA 5E 7C E0 1F` JMP far 1FE0:7C5E (the relocated copy)
  - 1FE0:7C5E `8E D8 8E D0` MOV DS, AX; MOV SS, AX (AX=1FE0)
- **Some unknown number of instructions later, CPU is at 1FE0:???0F
  with bytes `00 00 00 00`** (the "zero sled" — Gemini consult
  20260517_024459.txt Q2 analysis).
- PIT IRQ 0 keeps firing; IRET returns to the next 0x180-bytes-later
  zero address; CPU drifts through uninitialised FreeDOS kernel area
  forever, never executing actual kernel code, never producing screen
  output.

Per-instr path at the same point (5M architectural instructions in)
reaches the FreeDOS install welcome screen in full colour.

## What we ruled OUT

| Hypothesis | Test | Result |
|---|---|---|
| **SMC cache invalidation failure (Gemini hypothesis #1)** | Added `X86JsonCpu._activeCpu` static + `NotifyExternalMemoryWrite` static hook. Wired `MemWrite8` extern + `Fdc8272.ReadDataExecute` DMA loop to call `BlockCache.NotifyMemoryWrite(addr)` per byte. | **NO fix**. Symptom unchanged. (Fix still landed as cleanup — it WAS a real bug, just not the one causing the divergence.) |
| **Intra-block LLVM optimisation (mem2reg / GVN reordering)** | `APR_X86_BLOCK_MAX=1` env var forces block size to one instruction = effectively per-instr through the JIT compiler, defeating all multi-instruction optimisations. | **NO fix**. Black screen, identical symptom. Rules out intra-block reordering. |
| **`MOV SS` / IRQ-window violation (Gemini hypothesis #3)** | Added `APR_DISABLE_PIT_IRQ` env var that skips `Pic8259.AssertIrq(0)` from `PcPit`. Diagnostic-only; reverted from the committed code. | **NO fix**. Black screen even with PIT IRQ never firing. Rules out IRQ timing. |

## What we still suspect

Gemini consult 20260517_024459.txt narrowed it to two remaining classes
after block-size=1 ruled out intra-block bugs:

- **Memory aliasing across the C# extern boundary**. Per-instr CPU
  reads/writes go directly through `X86Memory.ReadByte`/`WriteByte` in
  managed C#. Block-JIT goes through the unmanaged `MemRead8`/`MemWrite8`
  externs (declared `[UnmanagedCallersOnly]`). If the JIT-emitted IR
  treats two consecutive memory ops as not aliasing (no TBAA / volatile
  metadata) and LLVM reorders or caches them, observable behaviour
  diverges from per-instr's strict-order managed loop.
- **Lazy EFLAGS calculation diverging in some specific opcode**.
  Block-JIT may defer flag computation while per-instr always commits
  it. A `CMP` / `TEST` / shift inside the FreeDOS kernel-load code path
  could produce the wrong condition under block-JIT, taking the wrong
  branch and ending in the zero-sled.

Both require an instruction-by-instruction lockstep diff against per-instr
to pinpoint the first divergent state. Quick screen-scrape comparisons
won't be enough — the divergent instruction is buried among millions of
correct ones.

## Recommended next-sprint plan

1. **Wire `LockstepDiff` to x86** — `src/AprCpu.Core/Validation/LockstepDiff.cs`
   already provides the generic harness via `ISteppableCpu`. Wrap two
   `X86JsonCpu` instances (one with `enableBlockJit=false`, one with
   `=true`), share memory carefully (one of them needs a memory-mirror
   so writes don't interfere), step both forward, assert AX..DI + FLAGS
   + DS/ES/SS/CS:IP match at each architectural-instruction boundary.
2. **Quirk**: under block-JIT each Step() executes a whole block. Lockstep
   needs to:
   - Capture next-block address from JIT's compiled IR (BlockDetector
     already returns the block's instruction list).
   - Step per-instr CPU forward exactly N instructions to match.
3. **Disable interrupts** during the diff so PIT/FDC don't fire at
   different points in the two runs (Gemini hypothesis: false-positive
   divergences). Force-mask IRQs via the PIC IMR at startup or via the
   `APR_DISABLE_PIT_IRQ` env var (re-add after this commit if useful).
4. **Bisect on block start address**. Once divergence found, dump the
   LLVM IR for that specific block (`APR_LLVM_IR_DUMP=ADDR` env var) and
   inspect the load/store ordering, TBAA metadata, alloca shadow
   semantics for that block's specific opcode mix.

Estimated effort: 3-5 days.
