# Phase 30.15d — Verified Block-JIT framework design

> **Status**: 🔵 design spec — implementation deferred to Phase 30.15d-impl.
> Written 2026-05-17 after Phase 30.15b/c uncovered the *second* class
> of block-JIT divergence (memory-write divergence) deep into FreeDOS
> boot and 30.15b uncovered the *first* (IP-prewrite linear-vs-IP bug).
> Both bugs were found *reactively* via post-hoc lockstep + cycle-budget
> bisection — slow, manual, and x86-specific. This doc designs a
> *proactive*, *generic*, *cheap* framework feature that catches the
> same class of bugs the moment a single block exits.

## 1 — Problem statement

Adding a new CPU backend (so far: ARM7TDMI, LR35902, 2A03, x86-16) to
the JSON-spec → LLVM JIT pipeline is straightforward for the happy
path (single-instruction interpretation matches the spec). Bugs in the
**block-JIT** layer are far harder to surface:

- Per-instruction unit tests (Tom Harte SST, blargg cpu_test5,
  jsmolka arm/thumb) catch single-opcode semantic errors but **not**
  cross-instruction interactions within a block (e.g. shadow-alloca
  drain ordering, LLVM optimisation reorderings, PC-pre-write timing).
- Lockstep diff (`apr-pc --lockstep-bjit`) eventually surfaces the
  divergence but **at the wrong granularity**: the bug fires inside a
  block, the *symptom* shows up millions of architectural instructions
  later when corrupted memory or a stale register is finally read.
  Bisection over a multi-million-step boot is expensive and manual.
- The same class of bug **will recur** for every future CPU backend
  (R3000A, R4300i, M68K, ...) — these are not one-off bugs but
  systematic blind spots in the framework.

The two recently-found bugs illustrate the cost:

| Bug | Found at | Cost to find | Reactive tool used |
|---|---|---|---|
| 30.15b — IP pre-write linear-vs-IP | step 25,282 | ~6 hr investigation + custom lockstep wiring | LockstepDiff CPU state |
| 30.15c — memory write divergence at 0x279C0 | step ~356,065 | still open | LockstepDiff + manual mem-region compare |

If the framework had detected the IP bug **at the first block-JIT
block that touched a low-CS segment** (step ~25,000-ish), it would
have reported "block X's compiled output writes IP slot to 0x3F7 but
per-instr writes 0xF7 — divergence in MOV r/m16 emitter line 317".
Hours saved, not just for x86 but for every future CPU that re-treads
the same patterns.

## 2 — Existing infrastructure audit

The framework already has pieces that solve **adjacent** problems but
do NOT solve "semantic divergence between block-JIT and per-instr
within a single block":

| Component | What it does | Why insufficient for this problem |
|---|---|---|
| `AprCpu.Core/Validation/LockstepDiff.cs` | Generic outer-loop comparator: step A & B alternately, compare register snapshot | Per-instruction only; doesn't cover memory side-effects; reactive (millions of steps deep) |
| `ISteppableCpu` interface | Step + Snapshot + ReadByteFromBus contract | OK as a starting point; will be reused |
| `memory_write_8_sync` extern (GB) | Block exits when MMIO write changes HW state | Solves MMIO-needs-exit, not write-semantics-divergence |
| `EmitSmcCoverageNotify` (GB) | Invalidates cached blocks when RAM write hits code area | Solves code-page-overwrite, not write-semantics-divergence |
| `Lr35902WramBase` / `Mos6502WramBase` inline fast-paths | Direct GEP-store to RAM region without bus extern | Performance optimisation; doesn't help with correctness |
| Tom Harte SST harnesses | Per-opcode (initial state → 1 instr → expected state + bus log) | Catches single-instruction bugs only; misses block-level interactions |
| Phase 30.15b `--lockstep-bjit` + `APR_LOCKSTEP_*` env vars | x86-specific lockstep with CPU + mem-region diff | Reactive (post-hoc), x86-only, requires manual bisection, no per-block granularity |

**Gap analysis**: the existing tools form a U-shape: per-opcode tests
catch instruction-level bugs, full-program lockstep catches eventual
divergence. The middle layer — **per-block semantic equivalence
between the JIT'd block and an interpreter executing the same N
instructions** — is missing.

## 3 — Design principles

1. **Per-block, not per-program.** Verify *each compiled block* the
   first time the JIT runs it. Catches the bug at the bug's instruction
   instead of at the eventual symptom thousands of steps later.
2. **Opt-in via env var or CLI flag** (`APR_VERIFY_JIT_BLOCKS=1` or
   `--verify-blocks`). Off in production; the verification has
   non-trivial cost (~2× CPU + memory trace bookkeeping).
3. **Generic across CPU backends.** A new CPU added in the future
   should pick up verification automatically by implementing the
   already-generic `ISteppableCpu` + one new optional interface
   (`IBlockBoundedSteppableCpu`).
4. **Three comparison axes**, each independently catchable:
   - **CPU state** at block exit (already covered by lockstep)
   - **Memory write trace** at block exit (Gemini Q4 — the missing piece)
   - **External side-effects log** (port I/O, MMIO writes, IRQ asserts)
5. **Cheap when verification disabled** (zero IR change, zero runtime cost).
6. **Reproducibility**: every reported divergence must include the block's
   `linearPc`, the matched-prefix CPU+mem state, and enough context to
   re-run that single block in isolation.

## 4 — Architecture

### 4.1 Component overview

```
                ┌─────────────────────────────────────────────────┐
                │            Per-CPU harness CLI                  │
                │  (PcLockstep / GbLockstep / NesLockstep / ...)  │
                └──────────┬───────────────────────────────┬──────┘
                           │                               │
                           ▼                               ▼
              ┌─────────────────────────┐    ┌──────────────────────────┐
              │  VerifiedBlockJitRunner │    │  per-CPU env A (interp)  │
              │  (generic, in           │◀───┤  per-CPU env B (JIT)     │
              │  AprCpu.Core)           │    │  ↑ shared spec + memory  │
              └──────────┬──────────────┘    │  ↑ separate state buf    │
                         │                   └──────────────────────────┘
                         ▼
              ┌────────────────────────────────────┐
              │   3-axis block-boundary verifier   │
              │  ┌─────────────────────────────┐   │
              │  │ axis 1: CPU state diff      │   │
              │  │ axis 2: mem-write trace diff│   │
              │  │ axis 3: side-effect log diff│   │
              │  └─────────────────────────────┘   │
              └────────────────────────────────────┘
```

### 4.2 Per-block verification flow

For each block the JIT runs (first execution only, or every execution
if `APR_VERIFY_JIT_BLOCKS_ALWAYS=1`):

```
1. snapshot = freeze(env_jit.state, env_jit.memory)
2. env_jit.RunBlock()                        // executes JIT-compiled block
   ↳ captures writeTraceJit = (addr, val, size)[]
   ↳ captures sideEffectsJit = (port_out, irq_assert, ...)[]
3. env_interp.LoadSnapshot(snapshot)         // identical entry state
4. for i in 0..block.Instructions.Count:
       env_interp.Step()
   ↳ captures writeTraceInterp = (addr, val, size)[]
   ↳ captures sideEffectsInterp = (...)[]
5. Compare:
       env_jit.state.cpu == env_interp.state.cpu  ? YES → next axis
       writeTraceJit == writeTraceInterp          ? YES → next axis
       sideEffectsJit == sideEffectsInterp        ? YES → block verified, commit JIT result
6. If any axis fails:
       report (linearPc, instruction index within block, axis, diff)
       optionally dump LLVM IR for the block to temp/jit-diverged-<pc>.ll
       abort or continue (configurable)
7. If all pass:
       discard env_interp state (was just a verifier); env_jit state is canonical
```

**Key insight**: A and B share the SAME memory before the block runs
(via snapshot). A's writes mutate one copy; B's writes mutate another
copy. After the block both copies are diffed. The interp is a
*verifier*, not a *peer* — we only need its mem-write trace + final
state, not to keep its memory alive across blocks.

### 4.3 Per-CPU contract

Existing `ISteppableCpu` stays unchanged. Add ONE new optional
interface:

```csharp
namespace AprCpu.Core.Validation;

/// <summary>
/// CPUs that opt into block-boundary verification implement this.
/// Lets the verifier framework drive an interp-only "verifier" pass
/// alongside a JIT-driven "primary" pass, then diff at block exit.
/// </summary>
public interface IBlockBoundedSteppableCpu : ISteppableCpu
{
    /// <summary>
    /// Number of architectural instructions in the most-recently-
    /// executed block. Used by the verifier to step the interp the
    /// same number of times. -1 if the last call was not a block
    /// (e.g. fallback per-instr path).
    /// </summary>
    int LastBlockInstructionCount { get; }

    /// <summary>
    /// Force the next Step() to execute exactly one architectural
    /// instruction (no block JIT). Used by the verifier when driving
    /// the interp side.
    /// </summary>
    void StepOneArchitecturalInstruction();

    /// <summary>
    /// Begin recording memory writes + side effects into the supplied
    /// trace buffer. Subsequent Step()/RunBlock() calls append.
    /// Returns a token to pass to EndTrace().
    /// </summary>
    object BeginTrace(IBlockTraceSink sink);

    /// <summary>Stop recording (passes back to no-op trace sink).</summary>
    void EndTrace(object token);

    /// <summary>
    /// Capture the full guest memory + CPU state into an opaque
    /// snapshot the verifier can later LoadSnapshot back. Snapshots
    /// can be coarse (full 1MB memcpy) or fine (CoW page table).
    /// First implementation: full memcpy.
    /// </summary>
    object SnapshotMemoryState();
    void   LoadMemoryState(object snapshot);
}

public interface IBlockTraceSink
{
    void RecordMemWrite(uint addr, ulong value, byte sizeBytes);
    void RecordPortWrite(ushort port, ushort value, byte sizeBytes);
    void RecordIrqAssert(byte vector);
}
```

For backwards compatibility, `ISteppableCpu` works unchanged for
backends that don't opt in (lockstep harness keeps working for them).

### 4.4 Memory-write trace buffer

Append-only ring per env. Entry shape:

```csharp
public readonly record struct MemWriteRecord(
    int  InstrIndexWithinBlock,
    uint LinearAddr,
    ulong Value,        // zero-extended for u8/u16/u32 writes
    byte SizeBytes,     // 1/2/4
    uint CsIp);         // for x86; 0 for non-segmented archs
```

Buffer is `MemWriteRecord[64]` (per block, since blocks rarely exceed
~64 instructions × few writes each). If overflow, mark "trace
truncated, divergence-detection partial".

Comparator iterates A's buffer and B's buffer side-by-side, reports
first mismatch with full context. Per-CPU implementation appends to
buffer from inside `MemWrite8` extern when tracing is active (single
TLS pointer check; near-zero overhead when off).

### 4.5 Side-effects log

Same shape as mem-write trace but for `OUT` / IRQ assert. Optional;
many CPUs (GB, NES) don't have port I/O. x86 includes it.

### 4.6 Snapshot storage

V1: full memcpy of the guest RAM. For 1MB x86 system → 1MB memcpy per
verified block. With 64-instr blocks at 1MHz emulation ≈ 15k blocks /
sec → 15GB/s memory bandwidth. Acceptable for verification mode.

V2: per-block CoW page table — only copy pages that the block writes.
Optimisation deferred; V1 is the correctness baseline.

## 6 — Performance / cost analysis

| Mode | CPU cost | Memory cost | When to use |
|---|---|---|---|
| Verification OFF (default) | 0% | 0% | Production runs, CI matrix |
| `--verify-blocks` first-execution only | ~30% slower (interp runs once per cached block) | +1× RAM (snapshot) | Local dev / bug hunts |
| `--verify-blocks-always` | ~50-100% slower (interp runs every block invocation) | +1× RAM | Pre-commit gating |
| Differential fuzzing | independent (offline) | independent | Nightly CI; new-CPU bring-up |

Negligible overhead when off because:
- Trace sink is `null` → no-op record functions
- Snapshot calls gated by `if (verifyMode) ...`
- IR emission unchanged

## 8 — Test plan

1. **Self-test**: lockstep two per-instr CPUs (A and B both no-JIT)
   on a known-good test ROM → must report NoDiff. Validates trace +
   snapshot mechanics.
2. **Regression**: run the Phase 30.15b PC-prewrite bug `pcxtbios.bin`
   workload with the *pre-fix* `BlockFunctionBuilder` → must surface
   the divergence at block ≈ 100 (long before step 25,282), pointing
   at the specific instruction encoding `8B 17` MOV DX, [BX].
3. **Fuzz**: random 8086 instruction sequences (length 1-32) seeded
   from `test-roms/x86/29.11-fpu-integration.bin` → 10,000 sequences,
   0 divergences expected.
4. **CI gate**: every PR that touches `BlockFunctionBuilder.cs`,
   `AllocaSlotProvider.cs`, or any `*Emitters.cs` triggers a 1-minute
   verify-blocks run on a representative workload per backend.

## 9 — Open questions

- **Snapshot at instruction granularity?** §4.2 snapshots once per
  block. If the divergent instruction is the *third* of a 64-instr
  block, we still need to bisect within the block. Maybe collect
  per-instr trace and report instruction index within block. Cheap
  if `LastBlockInstructionCount` is exposed (it is).
- **MMIO read divergence?** Per-CPU read externs could have side
  effects (PIT counter latch, PIC ack). Trace + compare reads too?
  Probably yes for `--verify-blocks-strict` mode; off by default since
  reads with side-effects are rare and per-CPU implementations may
  legitimately differ in read ordering.
- **Re-compile during verification?** If the JIT block has SMC and
  gets invalidated mid-verification, the next block execution recompiles.
  The verifier shouldn't trigger re-verification of the same block
  unless its `generation` field changes — track generation in the
  cache key.
- **Cross-block defer / pending state?** GB's `defer` micro-op
  schedules a delayed effect (e.g. EI). If a defer body straddles the
  block boundary, the trace records the deferred write inside the
  NEXT block, not the originating one. Verifier comparator needs to
  match by `(linearPc, instructionIndexWithinBlock)` not by absolute
  step count to handle this.

## 10 — Open security / data concerns

None. Verification reads and writes only guest memory + spec data;
no host-side state.

## 11 — Why not just "shadow JIT"?

A common alternative is to run JIT and interp simultaneously and
sync-compare every step. The cost is per-step `1× JIT + 1× interp`
overhead **forever**. Our design only runs the interp **per cached
block**, **once** per cache entry. With a ~1k block cache that
amortises to near-zero overhead for long-running workloads.
