## 1 — 問題陳述

加新 CPU backend（目前：ARM7TDMI、LR35902、2A03、x86-16）到 JSON-spec →
LLVM JIT pipeline 對 happy path 是直接的（single-instruction interpretation
match spec）。**Block-JIT** 層的 bug 難浮現很多：

- Per-instruction unit test（Tom Harte SST、blargg cpu_test5、jsmolka
  arm/thumb）抓 single-opcode semantic error、但 **不抓** block 內的
  cross-instruction 互動（例如 shadow-alloca drain ordering、LLVM
  optimization reorder、PC-pre-write timing）。
- Lockstep diff（`apr-pc --lockstep-bjit`）最終會浮現 divergence、但
  **粒度錯**：bug 在 block 內 fire、*症狀* 在數百萬個 architectural
  instruction 之後當 corrupted memory 或 stale register 終於被讀時才出來。
  在跑百萬步的 boot 上 bisect 又貴又手動。
- 同類 bug **會 recur** for 未來每個 CPU backend（R3000A、R4300i、M68K、…）
  — 這些不是 one-off bug、是 framework 的系統性 blind spot。

最近找到的兩個 bug 顯示成本：

| Bug | 在哪找到 | 找的成本 | 用的反應式工具 |
|---|---|---|---|
| 30.15b — IP pre-write linear-vs-IP | step 25,282 | ~6 hr investigation + 自寫 lockstep wiring | LockstepDiff CPU state |
| 30.15c — 0x279C0 memory write divergence | step ~356,065 | 還沒關 | LockstepDiff + 手動 mem-region 比 |

如果 framework 在 **第一個碰 low-CS segment 的 block-JIT block**（step
~25,000）就偵測到 IP bug、它會報「block X 的 compiled output 把 IP slot
寫 0x3F7 但 per-instr 寫 0xF7 — MOV r/m16 emitter line 317 divergence」。
省幾個小時、不只 x86、是每個未來重蹈同 pattern 的 CPU。

## 2 — 既有 infrastructure audit

Framework 已經有解 **鄰近** 問題的 piece、但 **不** 解「single block 內
block-JIT vs per-instr 的 semantic divergence」：

| Component | 做什麼 | 為何對這問題不夠 |
|---|---|---|
| `AprCpu.Core/Validation/LockstepDiff.cs` | Generic outer-loop comparator：交替 step A & B、比較 register snapshot | 只 per-instruction；不 cover memory side-effect；反應式（百萬步深處） |
| `ISteppableCpu` interface | Step + Snapshot + ReadByteFromBus contract | 起點 OK；會 reuse |
| `memory_write_8_sync` extern (GB) | MMIO write 改 HW state 時 block exit | 解 MMIO-needs-exit、不解 write-semantics-divergence |
| `EmitSmcCoverageNotify` (GB) | RAM write hit code 區時讓 cached block invalidate | 解 code-page-overwrite、不解 write-semantics-divergence |
| `Lr35902WramBase` / `Mos6502WramBase` inline fast-path | Direct GEP-store 到 RAM region、無 bus extern | Perf optimization；對正確性無幫助 |
| Tom Harte SST harness | Per-opcode（initial state → 1 instr → expected state + bus log） | 只抓 single-instruction bug；漏 block-level 互動 |
| Phase 30.15b `--lockstep-bjit` + `APR_LOCKSTEP_*` env var | x86-specific lockstep with CPU + mem-region diff | 反應式（post-hoc）、x86-only、要手動 bisect、無 per-block 粒度 |

**Gap analysis**：既有工具形成 U 形：per-opcode test 抓 instruction-level
bug、full-program lockstep 抓最終 divergence。中間層 — **JIT'd block 跟
跑同樣 N instruction 的 interpreter 之間的 per-block semantic 等價** —
不見。

## 3 — 設計原則

1. **Per-block、不 per-program**。在 JIT 第一次跑時驗證 *每個 compiled
   block*。在 bug 的 instruction 抓 bug、而不是幾千步後最終的 symptom。
2. **透過 env var 或 CLI flag opt-in**（`APR_VERIFY_JIT_BLOCKS=1` 或
   `--verify-blocks`）。生產關掉；驗證有 non-trivial cost（~2× CPU +
   memory trace bookkeeping）。
3. **Generic 跨 CPU backend**。未來加新 CPU 透過實作已經 generic 的
   `ISteppableCpu` + 一個新的 optional interface
   （`IBlockBoundedSteppableCpu`）自動拿到驗證。
4. **三個比較軸**、每個可獨立抓：
   - Block exit 的 **CPU state**（lockstep 已 cover）
   - Block exit 的 **memory write trace**（Gemini Q4 — 缺的 piece）
   - **External side-effect log**（port I/O、MMIO write、IRQ assert）
5. **驗證關掉時便宜**（零 IR 改、零 runtime cost）。
6. **可重現**：每個報的 divergence 必須包含 block 的 `linearPc`、matched-prefix
   CPU+mem state、跟足以獨立 re-run 那個 block 的 context。

### 4.1 Component overview

### 4.2 Per-block 驗證 flow

JIT 跑的每個 block（只第一次執行、或如果 `APR_VERIFY_JIT_BLOCKS_ALWAYS=1`
則每次執行）：

```
1. snapshot = freeze(env_jit.state, env_jit.memory)
2. env_jit.RunBlock()                        // 執行 JIT-compiled block
   ↳ 捕捉 writeTraceJit = (addr, val, size)[]
   ↳ 捕捉 sideEffectsJit = (port_out, irq_assert, ...)[]
3. env_interp.LoadSnapshot(snapshot)         // 一樣的 entry state
4. for i in 0..block.Instructions.Count:
       env_interp.Step()
   ↳ 捕捉 writeTraceInterp = (addr, val, size)[]
   ↳ 捕捉 sideEffectsInterp = (...)[]
5. 比較：
       env_jit.state.cpu == env_interp.state.cpu  ? YES → 下個軸
       writeTraceJit == writeTraceInterp          ? YES → 下個軸
       sideEffectsJit == sideEffectsInterp        ? YES → block verified、commit JIT 結果
6. 任何軸 fail：
       報 (linearPc、block 內 instruction index、軸、diff)
       選擇性 dump block LLVM IR 到 temp/jit-diverged-<pc>.ll
       abort 或 continue（可配置）
7. 全部 pass：
       丟 env_interp state（只是 verifier）；env_jit state 是 canonical
```

**關鍵 insight**：A 跟 B 在 block 跑之前 share **同個** memory（透過
snapshot）。A 的 write mutate 一份 copy；B 的 write mutate 另一份。
Block 之後兩份都 diff。Interp 是 *verifier*、不是 *peer* — 我們只需要
它的 mem-write trace + 最終 state、不需要它的 memory 跨 block 活著。

### 4.3 Per-CPU contract

既有 `ISteppableCpu` 不變。加一個新的 optional interface：

```csharp
namespace AprCpu.Core.Validation;

/// <summary>
/// Opt 進 block-boundary 驗證的 CPU 實作這個。
/// 讓 verifier framework 在 JIT-driven「primary」pass 旁邊驅動
/// interp-only「verifier」pass、然後 block exit diff。
/// </summary>
public interface IBlockBoundedSteppableCpu : ISteppableCpu
{
    /// <summary>
    /// 最近一次執行的 block 內的 architectural instruction 數量。
    /// Verifier 用它 step interp 同樣次數。-1 if 上次 call 不是 block
    /// （例如 fallback per-instr path）。
    /// </summary>
    int LastBlockInstructionCount { get; }

    /// <summary>
    /// 強迫下個 Step() 執行剛好一個 architectural instruction（無 block JIT）。
    /// Verifier 驅動 interp 端時用。
    /// </summary>
    void StepOneArchitecturalInstruction();

    /// <summary>
    /// 開始把 memory write + side effect record 到供的 trace buffer。
    /// 後續 Step()/RunBlock() call append。Return 一個 token 給 EndTrace()。
    /// </summary>
    object BeginTrace(IBlockTraceSink sink);

    /// <summary>停止 record（換回 no-op trace sink）。</summary>
    void EndTrace(object token);

    /// <summary>
    /// 捕捉完整 guest memory + CPU state 到一個 opaque snapshot、
    /// verifier 之後可以 LoadSnapshot 回。Snapshot 可粗（full 1MB memcpy）
    /// 或細（CoW page table）。第一個實作：full memcpy。
    /// </summary>
    object SnapshotMemoryState();
    void   LoadMemoryState(object snapshot);
}

public interface IBlockTraceSink
{
    void RecordMemWrite(uint addr, ulong value, byte sizeBytes);
    void RecordPortWrite(ushort port, ushort value, byte sizeBytes);
    void RecordIrqAssert(byte vector);
}
```

為了向後相容、不 opt-in 的 backend 用 `ISteppableCpu` 不變（lockstep
harness 對它們繼續 work）。

### 4.4 Memory-write trace buffer

Per env 的 append-only ring。Entry shape：

```csharp
public readonly record struct MemWriteRecord(
    int  InstrIndexWithinBlock,
    uint LinearAddr,
    ulong Value,        // u8/u16/u32 write zero-extend
    byte SizeBytes,     // 1/2/4
    uint CsIp);         // x86；non-segmented arch 為 0
```

Buffer 是 `MemWriteRecord[64]`（per block，因為 block 很少超過 ~64
instruction × 每個少數 write）。Overflow 時 mark「trace truncated、
divergence-detection partial」。

Comparator 並排 iterate A 跟 B buffer、報第一個 mismatch 帶完整 context。
Per-CPU 實作在 tracing active 時、`MemWrite8` extern 內 append 到 buffer
（single TLS pointer check；關掉時近零 overhead）。

### 4.5 Side-effect log

跟 mem-write trace 同形狀但 for `OUT` / IRQ assert。Optional；很多 CPU
（GB、NES）沒 port I/O。x86 包它。

### 4.6 Snapshot 儲存

V1：guest RAM 的 full memcpy。1MB x86 system → 每個 verified block 1MB
memcpy。1MHz emulation 下 64-instr block ≈ 15k blocks / sec → 15GB/s
memory 頻寬。驗證模式可接受。

V2：per-block CoW page table — 只 copy block 寫的 page。Optimization 延後；
V1 是正確性 baseline。

## 6 — 效能 / 成本分析

| 模式 | CPU 成本 | Memory 成本 | 何時用 |
|---|---|---|---|
| 驗證 OFF（預設） | 0% | 0% | 生產跑、CI matrix |
| `--verify-blocks` first-execution only | ~30% 慢（interp 每個 cached block 跑一次） | +1× RAM（snapshot） | Local dev / bug hunt |
| `--verify-blocks-always` | ~50-100% 慢（interp 每次 block invocation 都跑） | +1× RAM | Pre-commit gating |
| Differential fuzzing | 獨立（offline） | 獨立 | Nightly CI；新 CPU bring-up |

關掉時可忽略 overhead 因為：
- Trace sink 是 `null` → no-op record function
- Snapshot call gated by `if (verifyMode) ...`
- IR emission 不變

1. **Self-test**：lockstep 兩個 per-instr CPU（A 跟 B 都 no-JIT）在
   known-good test ROM → 必須報 NoDiff。驗證 trace + snapshot 機制。
2. **Regression**：跑 Phase 30.15b PC-prewrite bug `pcxtbios.bin`
   workload + *pre-fix* `BlockFunctionBuilder` → 必須在 block ≈ 100
   surface divergence（遠在 step 25,282 之前）、指向特定 instruction
   encoding `8B 17` MOV DX, [BX]。
3. **Fuzz**：random 8086 instruction sequence（length 1-32）seed 從
   `test-roms/x86/29.11-fpu-integration.bin` → 10,000 sequence、預期
   0 divergence。
4. **CI gate**：每個碰 `BlockFunctionBuilder.cs`、`AllocaSlotProvider.cs`、
   或任何 `*Emitters.cs` 的 PR 觸發每 backend 一個 representative workload
   的 1 分鐘 verify-blocks 跑。

## 9 — Open question

- **Instruction-粒度 snapshot？** §4.2 每 block 一個 snapshot。如果
  divergent instruction 是 64-instr block 的 *第三個*、我們還是要在
  block 內 bisect。可能 collect per-instr trace 並報 block 內 instruction
  index。便宜如果 `LastBlockInstructionCount` 暴露（它有）。
- **MMIO read divergence？** Per-CPU read extern 可能有 side effect
  （PIT counter latch、PIC ack）。Trace + 比 read 也？`--verify-blocks-strict`
  mode 可能 yes；預設 off 因為帶 side-effect 的 read 少、per-CPU 實作
  可能 legitimately 在 read ordering 上不同。
- **驗證期間 re-compile？** JIT block 有 SMC、驗證途中被 invalidate、
  下個 block 執行 recompile。Verifier 不該觸發同 block 的 re-verification
  除非它的 `generation` field 變 — cache key 追 generation。
- **跨 block 的 defer / pending state？** GB 的 `defer` micro-op 排
  delayed effect（例如 EI）。如果 defer body 跨 block 邊界、trace 在
  NEXT block 裡 record deferred write、不在 originating 那個。Verifier
  comparator 要靠 `(linearPc, instructionIndexWithinBlock)` match、
  不靠 absolute step count、來 handle 這個。

## 10 — Open security / data 顧慮

無。驗證只 read + write guest memory + spec data；無 host-side state。

## 11 — 為什麼不就「shadow JIT」？

常見 alternative 是同時跑 JIT 跟 interp、每 step sync-compare。Cost 是
per-step `1× JIT + 1× interp` overhead **永遠**。我們的設計 interp
只 **per cached block** 跑、每個 cache entry **一次**。~1k block cache
amortize 到長時間 workload 近零 overhead。

### Framework 證明的價值

Iteration  | 結果 | 原因
---|---|---
Initial（5.4b 前） | Verifier 在 block #39,836 因 cycling port-counter false positive crash | PortBus state 跨 env 演化沒同步
5.4b 之後 | Verifier 在 block #2 diverge（錯 — JIT 跑了 1 instr 但 verifier 對 INTERP 跑 59） | `entry.InstructionCount`（compile-time）≠ 實際 runtime instr count
5.4b + 5.4c 之後 | 19,471 block 驗證 OK 之後在 pc=0xFE2A9 報 `AX: A=0x344 B=0x348` divergence | INTERP 的 IN AL,0x61 透過 JIT env PortBus（post-JIT state）route；PortBus.Active singleton 從沒切換
**5.4b + 5.4c + 5.4d 之後** | **1,000,000 block 驗證 OK（4.38M architectural instruction、~3 min runtime）；pcxtbios + FreeDOS boot path 無 divergence** | 三個層疊的 verifier-framework bug 全部修了；x86-16 block-JIT 在這深度跟 per-instr 一致
