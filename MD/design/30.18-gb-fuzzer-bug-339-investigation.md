## Symptom

`apr-gb --fuzz=100 --fuzz-blocks=50 --fuzz-seed=42 --fuzz-continue`
報 100 個 random ROM 中 ~2 divergence。在所有之前的 cleanup（STOP
pad-byte、HALT signal transfer、length-table 0x08 fix、LDI/LDD reorder、
cross-jump-follow gate off、SpecLinter clean）之後 rate 卡住。

Sample divergence（seed=42、iter 78、block @ $4DF5）：

```
PRE  PC=$4DF5 A=$4F F=$00 BC=$0013 DE=$00D8 HL=$014D
JIT  POST PC=$4E09 A=$4D F=$80   (= block-end PC, Z=1)
INT  POST PC=$003A A=$60 F=$20
```

Block 含 18 個指令（$4DF5..$4E08）的 random byte；最後一個指令
（$4E08 = 0x55 = LD D,L）不轉移 control。JIT 落在 end-of-block PC
（$4E09 = $4DF5 + total length）；INTERP 落在 $003A — 在 cart ROM 內、
不是 programmed IRQ vector。

## Bisection 結果（`APR_EARLY_EXIT_BLOCK_PC=4DF5 APR_EARLY_EXIT_INSTR_COUNT=N`）

| Cap N | 結果 | 含義 |
|---|---|---|
| 1 | match at $4DF5；div at next block ($4DF6) | instr 1 正確 |

## 考慮過 + 排除的假設

### 假設：IRQ delivery cadence 不對稱（Gemini 第一個猜）

Gemini 注意到 $003A = $0038 + 2（RST 38h vector + 1 instr）並建議
INTERP 每個 instruction 之間 poll IRQ 而 JIT 只在 block 邊界 poll。
**透過 code inspection 排除**：

  - `GbSteppableCpu.StepOneArchitecturalInstruction()` 呼叫
    `JsonCpu.StepOnePerInstr()` 它只呼叫 `StepOne()` — **無
    CheckInterrupts call**。
  - `VerifiedBlockJitRunner` 透過 N 次 `StepOneArchitecturalInstruction()`
    跑 INTERP；內 `RunCycles` IRQ poll path 不走。
  - 所以 JIT 跟 INTERP 都跳過 block-internal instruction 之間的 IRQ
    delivery。不對稱在 block 邊界存在（JIT `RunCycles` 在 `StepBlock`
    之後 poll；INTERP verifier path 不 poll），但 PRE state 跟 POST
    state 都在任何邊界 poll fire 之前 snapshot — JIT 的 post-block
    PC=$4E09 確認 JIT 側 exit 時也沒 take vector。

### 假設：`branch_cc` 內的 stale F flag（Gemini 第二個猜）

`branch_cc` 透過 `StackOps.ResolveFlagCond` → `ctx.GepStatusRegister(reg)`
（StackOps.cs:551）讀 F flag。**透過 code inspection 排除**：

  - `EmitContext.GepStatusRegister`（EmitContext.cs:313）set 時 route
    through `Slots`（`AllocaSlotProvider`）。
  - `BlockFunctionBuilder` 對任何 `GprWidthBits <= 16` 的 CPU enable
    alloca provider（BlockFunctionBuilder.cs:155-175），cover LR35902
    — 並把 F register 為 non-banked status reg。
  - 因此 branch_cc 從 alloca shadow 讀 F，它 inline 收 per-instruction
    update 並被 mem2reg promote 到純 SSA。「stale memory F」失敗模式
    不會發生。

## 剩什麼（Gemini 的 Option A：per-instruction trace）

Bug 必須是下列之一：
  - (a) 某個非 control-flow 指令 emitter（ALU / mem / stack）對
    特定 operand 組合在 JIT vs per-instr StepOne 產不同結果
  - (b) 多 instruction state 互動（alloca shadow drift、PC alloca write
    side effect、post-store register read）
  - (c) PC update logic — JIT 以 PC=$4E09（end-of-block）exit 但 INTERP
    StepOne path 在每 instruction 後保持 PC 自然推進。如果某序列
    （PUSH/POP、stack underflow 的 RET、跟後續 PC 算術耦合的 RST）
    在 INTERP 結束於 PC=$003A、JIT compile-time block walk 看不到。

最有信息的下一步是 **Option A** — per-instruction trace buffer 在
JIT 跟 INTERP 兩邊每 instruction 後 record (PC, A, F, BC, DE, HL, SP)、
然後並排 diff。實作大綱：

  1. 對 `JsonCpu` state 加 fixed-size ring buffer：`(ushort pc, byte
     a, f, b, c, d, e, h, l; ushort sp)[64]` 加 `byte idx`。
  2. 在 `JsonCpu.StepOnePerInstr`：StepOne call 後寫 state 到下個 slot。
  3. 在 `BlockFunctionBuilder`：每個 per-instruction post-block 結尾
     （branch 到 next pre/exit 之前）emit IR 寫同樣 field 到同 buffer。
  4. Divergence 時在 `GbFuzzer` 並排印 buffer。

這是 ~150 LoC 集中診斷、可以由 env var 把守、不影響 production block-JIT。

## Update（Phase 30.18r/s）— iter 79 bug 已解決

`APR_GB_IR_DUMP=ADDR` env-gate 加了（sequence-numbered file 讓 multi-iter
compile 不互覆）。檢查 iter 79 在 $0150 block 的 IR 揭露實際 root cause：

```
i8_exec:                                  ; JP $DBC9
  store i16 -9271, ptr %pc_local          ; JP 寫 $DBC9
  store i8 1, ptr %pc_written_ptr         ; PcWritten=1
  call set_ime_fn(i8 1)                   ; EI 的 deferred body
  sub cycles by 16
  store i16 349, ptr %pc_local            ; ← SYNC CLOBBER PC = $015D
  store i8 1, ptr %pc_written_ptr         ; PcWritten=1 again
```

SyncEmitter（從 EI 的 deferred body、被 DeferLowering 注在 JP 自己 step
之後）無條件寫 `bi.Pc + length`（$015D）到 PC、覆蓋 JP 的 $DBC9。
Fix：`ctx.PcWriteEmittedInCurrentInstruction` 為 true 時跳過 PC overwrite。
也讓 Branch/Call/Ret 用 WriteReg.MarkPcWritten 來 set 那個 flag。
Commit `8d376da`。

## Update 2（Phase 30.18t）— bisection 確認 PRIOR-BLOCK corruption

`APR_EARLY_EXIT_BLOCK_PC=4DF5 APR_EARLY_EXIT_INSTR_COUNT=1` 在 block #4
（$4DF6）而不是 block #3（$4DF5）產 divergence。Block #4 的 PRE state
顯示：
```
A=$9C F=$20 BC=$0013 D=$00 E=$4D H=$4D L=$4D SP=$FFFD
```

對比（uncap 的）block #3 PRE state at $4DF5：
```
PRE BLOCK #3: A=$4F F=$00 BC=$0013 D=$00 E=$4D H=$4D L=$4D SP=$FFFD
```

**兩個都顯示 H=$4D、E=$4D、L=$4D**。Corruption 在 block #3 開始時
就 ALREADY THERE。所以 H corruption 發生在 block #0、#1、或 #2
（不在 $4DF5 block 內）。

cap=1 IR for $4DF5（只 ADD A,L、1 instruction）顯示 clean init+exec+drain
無 write 到 r5_local (H) 或 r4_local (E)。行為跟 IR 一致 — block #3
本身正確保留 H/E。Bug 上游。

Block chain（從 BLOCKLEN trace、iter 78）：
  - 很多 $0010 run（interrupt vector area / random ROM）
  - $0100（NOP + JP $0150）
  - $0150（detected=18 actual=7 — branch early）
  - $0157（detected=11 actual=3 — branch early）
  - $4DF5（divergent block）

所以 $0150、$0157、或穿 $0010 的某條 path 在 corrupt H=$4D。

## Update 3（Phase 30.18u）— H=$4D 是 LEGITIMATE、不是 bug

`APR_GB_IR_DUMP=ALL` dump 每個 block。檢查 iter 78 在 $0150 的 block
揭露：

```
instr[0] pc=0x0150 word=0x3B  mnem=DEC  (DEC SP — 不碰 F/reg)
instr[1] pc=0x0151 word=0x65  mnem=LD   (0x65 = LD H, L — copy L 到 H)
```

所以 `$0151 LD H,L` 合法地把 L 的值（=$4D、post-BIOS 預設 HL=$014D
的 low byte）寫到 H。後續 state 的 H=$4D 是 CORRECT 行為、不是 corruption。

Update 2 的 H corruption 假設錯。兩個 backend 都正確透過 $0151 的
LD H,L 產 H=$4D。

## 那 iter 78 bug 到底 IS 什麼？

回到原始 divergence：JIT 跟 INTERP 都跑 $4DF5 block（18 instruction、
無 `writes_pc=always`、C=0 的 JR cc 不 taken）。JIT 在 PC=$4E09 結束
（block-end）。INTERP 在 PC=$003A 結束。

INTERP 要落在 $003A、它 18 個 architectural-step 執行中的某個必須把
PC 轉到那。手工 trace 過 instruction（帶 correct pre-state HL=$4D4D、
DE=$004D）：
  - 全部 instruction 是 LD/ALU/PUSH 除了 instr[6] 的 JR cc
  - JR cc：C=0（在 instr[3] 的 CP 之後）→ 不 taken
  - 3 個 PUSH（無 POP）match POST SP=$FFF7

最終 POST state（手工 trace、兩個 backend 都該產）：
  A=$4D F=$80 BC=$1313 DE=$9C4D HL=$4D9C SP=$FFF7 PC=$4E09

JIT 完全 match。INTERP 在 A/F/D/PC 不同。

**實際 bug 位置現在窄化**：在這些特定 instruction 之一的 per-instr
StepOne（INTERP path）內、或在 GbMemoryBus 如何 handle `LD (HL),A`
寫 $4D 到 address $4D9C（在 MBC ROM-bank-switch 範圍 $4000-$5FFF）
的 side-effect。

Next investigation：在 INTERP 的 StepOnePerInstr 捕捉 per-instruction
state（ring buffer）、跟期望 hand-trace 比較找哪個 instruction 第一個
diverge。

## Update 4（Phase 30.18u）— iter 78 的 ROOT CAUSE 找到 + FIX

檢查 GbMemoryBus.WriteByte 揭露：
```csharp
if (addr < 0x6000)  // $4000-$5FFF 範圍
{
    var hi = v & 0x3;
    if (_modeRamBank) _ramBank = hi;
    else              _romBank = (_romBank & 0x1F) | (hi << 5);
}
```

$4DF5 block 包含 instr[14] 的 `LD (HL),A` with HL=$4D9C（因為合法的
$0151 LD H,L + $4DF6 的 LD L,A 留 HL=$4D9C）。寫 $4D 到 address $4D9C
觸發 MBC1 ROM bank switch：`_romBank = (_romBank & 0x1F) | ((0x4D & 0x3)
<< 5) = 0x21`。

Switch 之後：
  - $4000-$7FFF 內 read 回 `SafeRom(offset + 0x21 * 0x4000)` =
    `SafeRom(0x84000+...)` → 32KB cart 越界 → 0xFF。
  - **0xFF = `RST 38h`**（jump 到 $0038）。

INTERP 從新（空）bank fetch fresh byte：read 0xFF → 執行 RST 38h →
PC = $0038。後續從 bank 0（$0000-$3FFF）的 fetch 是正常 random byte。
18 個 architectural instruction 之後 INTERP 落在 $003A。

JIT 用它已經 compile 的 IR 繼續（用 old-bank byte compile）、對 bank
switch 不知。在 $4E09 結束。

這完美 match Gemini 從之前 Gemini consult 的原始「Memory Bank Switch」
假設。原因對、但 Gemini 的具體 HL-shift sub-假設是紅鯡魚 — HL=$4D9C
來自合法 LD instruction、不是 register-write bug。

### Fix（Phase 30.18u）

加 `GbMemoryBus.SuppressMbcWrites` flag。Set 時、$0000-$7FFF 範圍內的
write 靜默忽略（無 bank switch、無 `_ramEnable` update）。`GbFuzzer.BuildEnv`
set 這個 flag 因為 random-ROM fuzzing 不測 MBC semantic — 它測 CPU
emitter 正確性。

也修 **BranchCc / CallCc / RetCc** emitter 的平行 bug：它們不 set
`ctx.PcWriteEmittedInCurrentInstruction`、所以 deferred EI 的 sync 在
conditional branch fire 之後跑時、它 clobber branch target。跟之前
JP/Call/Ret fix（Phase 30.18s）同 pattern。

驗過的 seed：
  - seed=42（原 iter 78 case）：**0 divergence**（之前 2）
  - seed=999：0 divergence（之前 1）
  - seed=1234：0 divergence
  - seed=100/2026/0：各 1 divergence、**但不同 bug**（F flag half-carry
    計算 mismatch — 另案 investigate）。

原本「JP/RST control transfer」bug #339 framing 結果不是關於 RST handling
— 而是 JIT 追蹤不到的 CPU+MBC 互動。透過改 fuzzer semantic（不是 emitter
logic）解決。

## Update 5（Phase 30.18x）— 最後剩下的 edge 是 TIMING/IRQ-cadence

更寬的 seed sweep（15 seed × 50 iter each）顯示 14/15 乾淨。seed=6 在
iter 2 有 1 divergence、這個 signature：

```
PRE  PC=\$003E SP=\$6CB0 …
JIT  POST PC=\$0048 SP=\$6CB0 (= STAT IRQ vector! SP 不變)
INT  POST PC=\$6F9A SP=\$6CB2 (= popped from stack, SP+=2)
```

Block 在 \$0048 以 RETI 結束。兩個 backend 都正確跑 RETI 的 pop（INTERP
明顯如此）。但 JIT 的 POST state 有 PC=\$0048 跟 SP=\$6CB0 — 跟 JIT
後做：CheckInterrupts → vector STAT IRQ → push popped-PC（\$6F9A）→
set PC=\$0048（STAT vector）一致。Push 把 SP 從 \$6CB2 → \$6CB0 restore。

INTERP via StepOnePerInstr 完全不 call CheckInterrupts（verifier
framework 只 loop StepOneArchitecturalInstruction × N）。所以 IRQ
從沒 vector。

這是文件化的 **IRQ-delivery-cadence 不對稱**、在 JIT（RunCycles 邊界
的 CheckInterrupts）跟 INTERP-verifier path（無 CheckInterrupts）之間。
是 framework 限制、不是 emitter bug。

Fix option：
  (a) 讓 verifier 的 INTERP loop 也在結尾 call CheckInterrupts
      （match JIT 在 block 邊界的 semantic）
  (b) 在 fuzzer 內 suppress IRQ delivery（例如每 block 強迫 IE=0）
  (c) 文件化為已知 edge case 並 skip 這種 iteration

## Update 6（Phase 30.18y）— 透過 option (a) RESOLVED

Reference impl `OldProject/AprGBemu/Emu_GB/Main.cs:528` 確認真硬體般
pattern：每個 `GB_CPU_exec()` 後 call `GB_Interrupt()`。所以 per-instruction
backend 應該在每個 instruction 後 poll IRQ。

實作（commit `f451988`）：
  - 加 `IBlockBoundedSteppableCpu.PollPendingIrqsAtBlockBoundary()`
    interface method（預設 no-op）。
  - `GbSteppableCpu` override 為 call 新的 `JsonCpu.CheckInterruptsAtBlockBoundary`
    public wrapper（它 call private `CheckInterrupts`）。
  - `VerifiedBlockJitRunner` 在 INTERP loop 後 call 這個 — 兩個 backend
    現在看到同 block-boundary cadence 的 IRQ delivery。

量化影響：
  - 之前：seed=6 1 div；15/16 seed clean
  - 之後：**全 16 seed clean**（1-15 + 42/100/999/2026/0/1234）

User 診斷是對的：「感覺上不是邏輯錯誤、而是 timing 精度問題」。Fix 在
framework 層（verifier cadence）work、不在 per-instruction emitter 層。

## 狀態 — iter 78 bug 仍 OPEN

Phase 30.18s 之後 GB fuzzer 從 2 → 1 divergence at seed=42。剩下的是
iter 78 at $4DF5 with random ROM。

IR-dump-driven 分析（iter 78 block at $4DF5）：
  - 18 個 instruction、無 `writes_pc: always` 邊界
  - instr[6] 的 JR cc with C=0（在 instr[3] 的 CP 之後）→ NOT taken
  - Block 線性跑到 PC=$4E09

JIT 跟 INTERP 都以 R8 state 顯示 H=$4D（= LD L,A at instr[1] 前的 old
L 值）跟 E=$4D 結束 — BUT list 內無 instruction 用那個值寫 H 或 E。

Gemini 假設 8-bit register setter shift-vs-mask bug（`HL = (HL << 8) | new_L`
而不是 `(HL & 0xFF00) | new_L`）。檢查 LD-r-r emit IR（Lr35902WriteR8Emitter）
— IT'S CORRECT。每個 ddd iteration 做 `select(cmp, raw, prev)`、只在
cmp=true 時 write、否則保留。i1（LD L,A）的 IR 顯示 H 的 load+select
(false, ...)+store-back path、H 不變。

所以 bug NOT 在 Gemini 猜的 WriteR8 emitter 內。H corruption 到 $4D
必須來自其他地方。下個 session investigate 的假設：
  - Spec 有 instruction 它的 step 錯誤寫 H/E（audit 所有 step list 看
    無意的 `lr35902_write_r8` 到 ddd=4 或 `write_reg_pair_named` 到
    HL/DE with stale value）
  - bus.Tick(N) 或 memory_write extern 在 corrupt CPU state（PUSH op
    改 SP+memory；LD (HL),A 寫；如果這些有 wild pointer 可能覆蓋 GPR slot）
  - alloca shadow drain（block exit 的 DrainShadowsToState）有 register-index
    mismatch 寫錯 slot

Diagnostic 下一步：APR_GB_FORCE_BUDGET=1 + iter 78 single-step。
budget=1（強迫 effective 1-instr block）下 H 停 $01、normal budget 下
結尾 $4D、bug 是 multi-instruction 互動。budget=1 H=$4D 也、是 per-instruction。
