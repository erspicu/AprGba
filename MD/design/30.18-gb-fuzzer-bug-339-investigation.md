## Symptom

`apr-gb --fuzz=100 --fuzz-blocks=50 --fuzz-seed=42 --fuzz-continue`
reports ~2 divergences out of 100 random ROMs. After all earlier cleanup
(STOP pad-byte, HALT signal transfer, length-table 0x08 fix, LDI/LDD
reorder, cross-jump-follow gated to off, SpecLinter clean) the rate is
stuck.

Sample divergence (seed=42, iter 78, block @ $4DF5):

```
PRE  PC=$4DF5 A=$4F F=$00 BC=$0013 DE=$00D8 HL=$014D
JIT  POST PC=$4E09 A=$4D F=$80   (= block-end PC, Z=1)
INT  POST PC=$003A A=$60 F=$20
```

The block contains 18 instructions ($4DF5..$4E08) of random bytes; the
last instruction ($4E08 = 0x55 = LD D,L) does not transfer control.
JIT lands at end-of-block PC ($4E09 = $4DF5 + total length); INTERP
lands at $003A — INSIDE the cart ROM, not a programmed IRQ vector.

## Bisection results (`APR_EARLY_EXIT_BLOCK_PC=4DF5 APR_EARLY_EXIT_INSTR_COUNT=N`)

| Cap N | Result | Implication |
|---|---|---|
| 1 | match at $4DF5; div at next block ($4DF6) | instr 1 correct |
| 2 | match at $4DF6; div at next block ($4DF7) | instrs 1-2 correct |
| 3..17 | same pattern — div moves to next block | instrs 1..K correct |
| 18 (no cap) | div at $4E09 | bug surfaces |

Gemini reading: the bug is in the uncapped tail (instruction 18 or
a multi-instruction effect that requires the full block to manifest).
Bisection confirms instructions 1..K execute identically; divergence
strictly happens after the cap point.

## Hypotheses considered + ruled out

### Hypothesis: IRQ delivery cadence asymmetry (Gemini's first guess)

Gemini noted $003A = $0038 + 2 (RST 38h vector + 1 instr) and proposed
that INTERP polls IRQ between every instruction while JIT polls only
at block boundary. **Ruled out** by code inspection:

  - `GbSteppableCpu.StepOneArchitecturalInstruction()` calls
    `JsonCpu.StepOnePerInstr()` which calls `StepOne()` ONLY — **no
    CheckInterrupts call**.
  - `VerifiedBlockJitRunner` runs INTERP via N times
    `StepOneArchitecturalInstruction()`; the inner `RunCycles` IRQ poll
    path is NOT taken.
  - So both JIT and INTERP skip IRQ delivery between block-internal
    instructions. The asymmetry exists at block BOUNDARIES (JIT
    `RunCycles` polls after `StepBlock`; INTERP verifier path doesn't),
    but both PRE state and POST state are snapshotted before any
    boundary poll fires — and JIT's post-block PC=$4E09 confirms the
    JIT side also did not take a vector at exit.

### Hypothesis: stale F flag in `branch_cc` (Gemini's second guess)

`branch_cc` reads the F flag via `StackOps.ResolveFlagCond` →
`ctx.GepStatusRegister(reg)` (StackOps.cs:551). **Ruled out** by code
inspection:

  - `EmitContext.GepStatusRegister` (EmitContext.cs:313) routes through
    `Slots` (the `AllocaSlotProvider`) when set.
  - `BlockFunctionBuilder` enables the alloca provider for any CPU
    with `GprWidthBits <= 16` (BlockFunctionBuilder.cs:155-175), which
    covers LR35902 — and registers F as a non-banked status reg.
  - Therefore branch_cc loads F from the alloca shadow, which receives
    per-instruction updates inline and gets promoted to pure SSA by
    mem2reg. The "stale memory F" failure mode cannot happen.

## What remains (Option A from Gemini: per-instruction trace)

The bug must be one of:
  - (a) Some non-control-flow instruction emitter (ALU / mem / stack)
    produces a different result in JIT vs per-instr StepOne for a
    specific operand combination
  - (b) A multi-instruction state interaction (alloca shadow drift,
    PC alloca write side effect, post-store register read)
  - (c) PC update logic — JIT exits with PC=$4E09 (end-of-block) but
    INTERP's StepOne path keeps PC at the natural advance after each
    instruction. If some sequence (PUSH/POP, RET via stack underflow,
    RST coupled with subsequent PC arithmetic) ends with PC=$003A
    in INTERP, JIT's compile-time block walk wouldn't see it.

The most informative next step is **Option A** — per-instruction trace
buffer that records (PC, A, F, BC, DE, HL, SP) after every instruction
on BOTH JIT and INTERP, then diff side-by-side. Implementation outline:

  1. Add a fixed-size ring buffer to `JsonCpu` state: `(ushort pc,
     byte a, f, b, c, d, e, h, l; ushort sp)[64]` plus `byte idx`.
  2. In `JsonCpu.StepOnePerInstr`: after the StepOne call, write
     state to the next slot.
  3. In `BlockFunctionBuilder`: at the end of each per-instruction
     post-block (before branching to the next pre/exit), emit IR
     that writes the same fields to the same buffer.
  4. In `GbFuzzer` on divergence: print both buffers side-by-side.

This is a ~150 LoC focused diagnostic that can be gated behind an env
var so it doesn't affect production block-JIT.

Re-running the GB fuzzer after Phase 30.18p/q (GBA R15 fixes) on

Expected decode of bytes 0x0150..0x015C (13 bytes, 9 instructions):

| PC  | Byte(s)  | Mnemonic       | Len |
|-----|----------|----------------|-----|
| 150 | 07       | RLCA           | 1   |
| 151 | 1F       | RRA            | 1   |
| 152 | 1E 1E    | LD E, $1E      | 2   |
| 154 | 64       | LD H, H        | 1   |
| 155 | 2E 19    | LD L, $19      | 2   |
| 157 | 69       | LD L, C        | 1   |
| 158 | 35       | DEC (HL)       | 1   |
| 159 | FB       | EI             | 1   |
| **15A** | **C3 C9 DB** | **JP $DBC9** | **3** |

`JP nn` has `writes_pc: "always"`, so BlockDetector SHOULD end the
block at the JP. Expected: 9 instructions, JIT exits at JP with
PC=$DBC9. INTERP also exits at JP with PC=$DBC9. **No divergence**.

But `APR_GB_TRACE_BLOCKLEN=1` shows at least one block at $0150

  - (a) 13 INSTRUCTIONS at $0150 = each byte treated as a 1-byte

Open question: is `[BLOCKLEN] detected=13 actual=13 pcWritten=0` from

## Update (Phase 30.18r/s) — iter 79 bug RESOLVED

`APR_GB_IR_DUMP=ADDR` env-gate added (sequence-numbered files so
multi-iter compiles don't overwrite). Inspecting iter 79's IR for the
$0150 block revealed the actual root cause:

```
i8_exec:                                  ; JP $DBC9
  store i16 -9271, ptr %pc_local          ; JP wrote $DBC9
  store i8 1, ptr %pc_written_ptr         ; PcWritten=1
  call set_ime_fn(i8 1)                   ; EI's deferred body
  sub cycles by 16
  store i16 349, ptr %pc_local            ; ← SYNC CLOBBERED PC = $015D
  store i8 1, ptr %pc_written_ptr         ; PcWritten=1 again
```

The SyncEmitter (from EI's deferred body, injected after JP's own
steps by DeferLowering) unconditionally wrote `bi.Pc + length`
($015D) to PC, overwriting JP's $DBC9. Fix: skip the PC overwrite
when `ctx.PcWriteEmittedInCurrentInstruction` is true. Also made
Branch/Call/Ret use WriteReg.MarkPcWritten so they set that flag.
Commit `8d376da`.

## Update 2 (Phase 30.18t) — bisection confirms PRIOR-BLOCK corruption

`APR_EARLY_EXIT_BLOCK_PC=4DF5 APR_EARLY_EXIT_INSTR_COUNT=1` produces
divergence at block #4 ($4DF6) instead of block #3 ($4DF5). Block #4's
PRE state shows:
```
A=$9C F=$20 BC=$0013 D=$00 E=$4D H=$4D L=$4D SP=$FFFD
```

Comparing to the (uncapped) block #3 PRE state at $4DF5:
```
PRE BLOCK #3: A=$4F F=$00 BC=$0013 D=$00 E=$4D H=$4D L=$4D SP=$FFFD
```

**Both show H=$4D, E=$4D, L=$4D.** The corruption is ALREADY THERE when
block #3 starts. So the H corruption happens in blocks #0, #1, or #2
(NOT in the $4DF5 block).

The cap=1 IR for $4DF5 (only ADD A,L, 1 instruction) shows clean
init+exec+drain with no writes to r5_local (H) or r4_local (E).
Behavior is consistent with the IR — block #3 itself preserves H/E
correctly. The bug is upstream.

Block chain (from BLOCKLEN trace, iter 78):
  - Many runs at $0010 (interrupt vector area / random ROM)
  - $0100 (NOP + JP $0150)
  - $0150 (detected=18 actual=7 — branch early)
  - $0157 (detected=11 actual=3 — branch early)
  - $4DF5 (the divergent block)

So one of $0150, $0157, or some path through $0010 is corrupting H=$4D.

## Update 3 (Phase 30.18u) — H=$4D is LEGITIMATE, not a bug

`APR_GB_IR_DUMP=ALL` dumps every block. Inspecting iter 78's block at
$0150 reveals:

```
instr[0] pc=0x0150 word=0x3B  mnem=DEC  (DEC SP — doesn't touch F/regs)
instr[1] pc=0x0151 word=0x65  mnem=LD   (0x65 = LD H, L — copies L to H)
```

So `$0151 LD H,L` LEGITIMATELY writes L's value (=$4D, the post-BIOS
default HL=$014D low byte) to H. H=$4D in subsequent state is CORRECT
behaviour, not a corruption.

The H corruption hypothesis from Update 2 was wrong. Both backends
correctly produce H=$4D via the LD H,L at $0151.

## So what IS the iter 78 bug then?

Reverting to the original divergence: JIT and INTERP both run the
$4DF5 block (18 instructions, no `writes_pc=always`, JR cc with
C=0 not taken). JIT ends at PC=$4E09 (block-end). INTERP ends at
PC=$003A.

For INTERP to land at $003A, one of its 18 architectural-step
executions must have transferred PC there. Hand trace through the
instructions (with corrected pre-state HL=$4D4D, DE=$004D):
  - All instructions are LD/ALU/PUSH except JR cc at instr[6]
  - JR cc: C=0 (after CP at instr[3]) → not taken
  - 3 PUSHes (no POPs) match POST SP=$FFF7

Final POST state (hand trace, both backends should produce):
  A=$4D F=$80 BC=$1313 DE=$9C4D HL=$4D9C SP=$FFF7 PC=$4E09

JIT matches this exactly. INTERP differs in A/F/D/PC.

**The actual bug location is now narrowed**: it's in the per-instr
StepOne (INTERP path) for one of these specific instructions, OR in
how the GbMemoryBus handles a side-effect of `LD (HL),A` writing $4D
to address $4D9C (which is in the MBC ROM-bank-switch range $4000-$5FFF).

Next investigation: capture per-instruction state in INTERP's
StepOnePerInstr (ring buffer), compare against expected hand-trace
to find which instruction first diverges.

## Update 4 (Phase 30.18u) — ROOT CAUSE FOUND + FIXED for iter 78

Inspecting GbMemoryBus.WriteByte revealed:
```csharp
if (addr < 0x6000)  // $4000-$5FFF range
{
    var hi = v & 0x3;
    if (_modeRamBank) _ramBank = hi;
    else              _romBank = (_romBank & 0x1F) | (hi << 5);
}
```

The block at $4DF5 includes `LD (HL),A` at instr[14] with HL=$4D9C
(due to legitimate LD H,L at $0151 + LD L,A at $4DF6 leaving HL=$4D9C).
Writing $4D to address $4D9C triggers MBC1 ROM bank switch:
`_romBank = (_romBank & 0x1F) | ((0x4D & 0x3) << 5) = 0x21`.

After switch:
  - Reads in $4000-$7FFF return `SafeRom(offset + 0x21 * 0x4000)` =
    `SafeRom(0x84000+...)` → out-of-bounds for 32KB cart → 0xFF.
  - **0xFF = `RST 38h`** (jumps to $0038).

INTERP fetches fresh bytes from the new (empty) bank: reads 0xFF →
executes RST 38h → PC = $0038. Subsequent fetches from bank 0
($0000-$3FFF) are normal random bytes. After 18 architectural
instructions INTERP lands at $003A.

JIT continues with its already-compiled IR (compiled with old-bank
bytes), oblivious to the bank switch. Ends at $4E09.

This perfectly matches Gemini's original "Memory Bank Switch" hypothesis
from the previous Gemini consultation. The cause was correct, but
Gemini's specific HL-shift sub-hypothesis was a red herring — HL=$4D9C
came from legitimate LD instructions, not a register-write bug.

### Fix (Phase 30.18u)

Added `GbMemoryBus.SuppressMbcWrites` flag. When set, writes in
$0000-$7FFF range are silently ignored (no bank switch, no
`_ramEnable` update). `GbFuzzer.BuildEnv` sets this flag because
random-ROM fuzzing isn't testing MBC semantics — it's testing CPU
emitter correctness.

Also fixed parallel bug in **BranchCc / CallCc / RetCc** emitters:
they didn't set `ctx.PcWriteEmittedInCurrentInstruction`, so when
deferred EI's sync ran AFTER the conditional branch fired, it
clobbered the branch target. Same pattern as the earlier JP/Call/Ret
fix (Phase 30.18s).

Verified seeds:
  - seed=42 (the original iter 78 case): **0 divergences** (was 2)
  - seed=999: 0 divergences (was 1)
  - seed=1234: 0 divergences
  - seed=100/2026/0: 1 divergence each, **but DIFFERENT bug** (F flag
    half-carry calculation mismatch — to investigate separately).

The original "JP/RST control transfer" bug #339 framing turned out
to NOT be about RST handling — it was about CPU+MBC interaction
that the JIT couldn't track. Resolved by changing fuzzer semantics
rather than emitter logic.

## Update 5 (Phase 30.18x) — last remaining edge is TIMING/IRQ-cadence

Wider seed sweep (15 seeds × 50 iter each) shows 14/15 clean. Seed=6
has 1 divergence at iter 2 with this signature:

```
PRE  PC=\$003E SP=\$6CB0 …
JIT  POST PC=\$0048 SP=\$6CB0 (= STAT IRQ vector! SP unchanged)
INT  POST PC=\$6F9A SP=\$6CB2 (= popped from stack, SP+=2)
```

Block ends in RETI at \$0048. Both backends correctly run RETI's pop
(INTERP visibly so). But JIT's POST state has PC=\$0048 and SP=\$6CB0
— consistent with JIT then doing: CheckInterrupts → vector STAT IRQ
→ push popped-PC (\$6F9A) → set PC=\$0048 (STAT vector). The push
restores SP from \$6CB2 → \$6CB0.

INTERP via StepOnePerInstr doesn't call CheckInterrupts at all
(verifier framework only loops StepOneArchitecturalInstruction × N).
So IRQ never vectors.

This is the documented **IRQ-delivery-cadence asymmetry** between
JIT (CheckInterrupts at RunCycles boundary) and INTERP-verifier path
(no CheckInterrupts). It's a framework limitation, not an emitter bug.

Fix options:
  (a) Make verifier's INTERP loop also call CheckInterrupts at the end
      (matches JIT semantics at block boundary)
  (b) Suppress IRQ delivery in fuzzer (e.g., force IE=0 each block)
  (c) Document as known edge case and skip such iterations

## Update 6 (Phase 30.18y) — RESOLVED via option (a)

Reference impl `OldProject/AprGBemu/Emu_GB/Main.cs:528` confirms
the real-hardware-like pattern: call `GB_Interrupt()` after every
`GB_CPU_exec()`. So the per-instruction backend SHOULD poll IRQ
after each instruction.

Implementation (commit `f451988`):
  - Added `IBlockBoundedSteppableCpu.PollPendingIrqsAtBlockBoundary()`
    interface method (default no-op).
  - `GbSteppableCpu` overrides to call new `JsonCpu.CheckInterruptsAtBlockBoundary`
    public wrapper (which calls private `CheckInterrupts`).
  - `VerifiedBlockJitRunner` calls this after the INTERP loop —
    both backends now see IRQ delivery at the same block-boundary
    cadence.

Quantified impact:
  - Before: seed=6 1 div; 15/16 seeds clean
  - After:  **all 16 seeds clean** (1-15 + 42/100/999/2026/0/1234)

User's diagnosis was correct: "感覺上不是邏輯錯誤，而是timing精度問題"
(feels like a timing precision issue, not logic error). The fix
operates at the framework level (verifier cadence) not per-instruction
emitter level.

## Status — iter 78 bug STILL OPEN

After Phase 30.18s the GB fuzzer is down from 2 → 1 divergence at
seed=42. The remaining one is iter 78 at $4DF5 with random ROM.

IR-dump-driven analysis (iter 78 block at $4DF5):
  - 18 instructions, no `writes_pc: always` boundary
  - JR cc at instr[6] with C=0 (after CP at instr[3]) → NOT taken
  - Block runs linearly to PC=$4E09

Both JIT and INTERP end with R8 state showing H=$4D (= old L value
before LD L,A at instr[1]) and E=$4D — BUT no instruction in the
list writes H or E with that value.

Gemini hypothesised an 8-bit register setter shift-vs-mask bug
(`HL = (HL << 8) | new_L` instead of `(HL & 0xFF00) | new_L`).
Inspected the LD-r-r emit IR (Lr35902WriteR8Emitter) — IT'S CORRECT.
Each ddd iteration does `select(cmp, raw, prev)`, only writes when
cmp=true, otherwise preserves. The IR for i1 (LD L,A) shows H's
load+select(false, ...)+store-back path, leaving H unchanged.

So the bug is NOT in the WriteR8 emitter as Gemini guessed. The
H corruption to $4D must come from somewhere else. Hypotheses to
investigate next session:
  - Spec has an instruction whose steps incorrectly write H/E
    (audit all step lists for unintended `lr35902_write_r8` to ddd=4
    or `write_reg_pair_named` to HL/DE with stale value)
  - The bus.Tick(N) or memory_write extern is corrupting CPU state
    (PUSH ops modify SP+memory; LD (HL),A writes; if any of these
    have a wild pointer they could overwrite the GPR slots)
  - The alloca shadow drain (DrainShadowsToState at block exit) has
    a register-index mismatch that writes the wrong slot

Diagnostic next step: APR_GB_FORCE_BUDGET=1 + iter 78 single-step.
If H stays $01 with budget=1 (forces effectively 1-instr blocks)
but ends $4D with normal budget, bug is multi-instruction
interaction. If H=$4D with budget=1 too, it's per-instruction.
