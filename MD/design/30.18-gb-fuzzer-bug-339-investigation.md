# Phase 30.18d (task #339) — GB fuzzer divergence investigation log

> **Status**: 🟡 **In progress** — code inspection complete; per-instruction
> trace buffer needed to localize the divergent instruction.

## Symptom

`apr-gb --fuzz=100 --fuzz-blocks=50 --fuzz-seed=42 --fuzz-continue`
reports ~2 divergences out of 100 random ROMs. After all earlier cleanup
(STOP pad-byte, HALT signal transfer, length-table 0x08 fix, LDI/LDD
reorder, cross-jump-follow gated to off, SpecLinter clean) the rate is
stuck.

Sample divergence (seed=42, iter 78, block @ $4DF5):

```
PRE  PC=$4DF5 A=$4F F=$00 BC=$0013 DE=$00D8 HL=$014D
JIT  POST PC=$4E09 A=$4D F=$80   (= block-end PC, Z=1)
INT  POST PC=$003A A=$60 F=$20
```

The block contains 18 instructions ($4DF5..$4E08) of random bytes; the
last instruction ($4E08 = 0x55 = LD D,L) does not transfer control.
JIT lands at end-of-block PC ($4E09 = $4DF5 + total length); INTERP
lands at $003A — INSIDE the cart ROM, not a programmed IRQ vector.

## Bisection results (`APR_EARLY_EXIT_BLOCK_PC=4DF5 APR_EARLY_EXIT_INSTR_COUNT=N`)

| Cap N | Result | Implication |
|---|---|---|
| 1 | match at $4DF5; div at next block ($4DF6) | instr 1 correct |
| 2 | match at $4DF6; div at next block ($4DF7) | instrs 1-2 correct |
| 3..17 | same pattern — div moves to next block | instrs 1..K correct |
| 18 (no cap) | div at $4E09 | bug surfaces |

Gemini reading: the bug is in the uncapped tail (instruction 18 or
a multi-instruction effect that requires the full block to manifest).
Bisection confirms instructions 1..K execute identically; divergence
strictly happens after the cap point.

## Hypotheses considered + ruled out

### Hypothesis: IRQ delivery cadence asymmetry (Gemini's first guess)

Gemini noted $003A = $0038 + 2 (RST 38h vector + 1 instr) and proposed
that INTERP polls IRQ between every instruction while JIT polls only
at block boundary. **Ruled out** by code inspection:

  - `GbSteppableCpu.StepOneArchitecturalInstruction()` calls
    `JsonCpu.StepOnePerInstr()` which calls `StepOne()` ONLY — **no
    CheckInterrupts call**.
  - `VerifiedBlockJitRunner` runs INTERP via N times
    `StepOneArchitecturalInstruction()`; the inner `RunCycles` IRQ poll
    path is NOT taken.
  - So both JIT and INTERP skip IRQ delivery between block-internal
    instructions. The asymmetry exists at block BOUNDARIES (JIT
    `RunCycles` polls after `StepBlock`; INTERP verifier path doesn't),
    but both PRE state and POST state are snapshotted before any
    boundary poll fires — and JIT's post-block PC=$4E09 confirms the
    JIT side also did not take a vector at exit.

### Hypothesis: stale F flag in `branch_cc` (Gemini's second guess)

`branch_cc` reads the F flag via `StackOps.ResolveFlagCond` →
`ctx.GepStatusRegister(reg)` (StackOps.cs:551). **Ruled out** by code
inspection:

  - `EmitContext.GepStatusRegister` (EmitContext.cs:313) routes through
    `Slots` (the `AllocaSlotProvider`) when set.
  - `BlockFunctionBuilder` enables the alloca provider for any CPU
    with `GprWidthBits <= 16` (BlockFunctionBuilder.cs:155-175), which
    covers LR35902 — and registers F as a non-banked status reg.
  - Therefore branch_cc loads F from the alloca shadow, which receives
    per-instruction updates inline and gets promoted to pure SSA by
    mem2reg. The "stale memory F" failure mode cannot happen.

## What remains (Option A from Gemini: per-instruction trace)

The bug must be one of:
  - (a) Some non-control-flow instruction emitter (ALU / mem / stack)
    produces a different result in JIT vs per-instr StepOne for a
    specific operand combination
  - (b) A multi-instruction state interaction (alloca shadow drift,
    PC alloca write side effect, post-store register read)
  - (c) PC update logic — JIT exits with PC=$4E09 (end-of-block) but
    INTERP's StepOne path keeps PC at the natural advance after each
    instruction. If some sequence (PUSH/POP, RET via stack underflow,
    RST coupled with subsequent PC arithmetic) ends with PC=$003A
    in INTERP, JIT's compile-time block walk wouldn't see it.

The most informative next step is **Option A** — per-instruction trace
buffer that records (PC, A, F, BC, DE, HL, SP) after every instruction
on BOTH JIT and INTERP, then diff side-by-side. Implementation outline:

  1. Add a fixed-size ring buffer to `JsonCpu` state: `(ushort pc,
     byte a, f, b, c, d, e, h, l; ushort sp)[64]` plus `byte idx`.
  2. In `JsonCpu.StepOnePerInstr`: after the StepOne call, write
     state to the next slot.
  3. In `BlockFunctionBuilder`: at the end of each per-instruction
     post-block (before branching to the next pre/exit), emit IR
     that writes the same fields to the same buffer.
  4. In `GbFuzzer` on divergence: print both buffers side-by-side.

This is a ~150 LoC focused diagnostic that can be gated behind an env
var so it doesn't affect production block-JIT.
