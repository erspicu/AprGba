# Phase 30.18d (task #339) — GB fuzzer divergence investigation log

> **Status**: 🟡 **In progress** — code inspection complete; per-instruction
> trace buffer needed to localize the divergent instruction.

## Symptom

`apr-gb --fuzz=100 --fuzz-blocks=50 --fuzz-seed=42 --fuzz-continue`
reports ~2 divergences out of 100 random ROMs. After all earlier cleanup
(STOP pad-byte, HALT signal transfer, length-table 0x08 fix, LDI/LDD
reorder, cross-jump-follow gated to off, SpecLinter clean) the rate is
stuck.

Sample divergence (seed=42, iter 78, block @ $4DF5):

```
PRE  PC=$4DF5 A=$4F F=$00 BC=$0013 DE=$00D8 HL=$014D
JIT  POST PC=$4E09 A=$4D F=$80   (= block-end PC, Z=1)
INT  POST PC=$003A A=$60 F=$20
```

The block contains 18 instructions ($4DF5..$4E08) of random bytes; the
last instruction ($4E08 = 0x55 = LD D,L) does not transfer control.
JIT lands at end-of-block PC ($4E09 = $4DF5 + total length); INTERP
lands at $003A — INSIDE the cart ROM, not a programmed IRQ vector.

## Hypotheses considered + ruled out

### Hypothesis: IRQ delivery cadence asymmetry (Gemini's first guess)

Gemini noted $003A = $0038 + 2 (RST 38h vector + 1 instr) and proposed
that INTERP polls IRQ between every instruction while JIT polls only
at block boundary. **Ruled out** by code inspection:

  - `GbSteppableCpu.StepOneArchitecturalInstruction()` calls
    `JsonCpu.StepOnePerInstr()` which calls `StepOne()` ONLY — **no
    CheckInterrupts call**.
  - `VerifiedBlockJitRunner` runs INTERP via N times
    `StepOneArchitecturalInstruction()`; the inner `RunCycles` IRQ poll
    path is NOT taken.
  - So both JIT and INTERP skip IRQ delivery between block-internal
    instructions. The asymmetry exists at block BOUNDARIES (JIT
    `RunCycles` polls after `StepBlock`; INTERP verifier path doesn't),
    but both PRE state and POST state are snapshotted before any
    boundary poll fires — and JIT's post-block PC=$4E09 confirms the
    JIT side also did not take a vector at exit.

### Hypothesis: stale F flag in `branch_cc` (Gemini's second guess)

`branch_cc` reads the F flag via `StackOps.ResolveFlagCond` →
`ctx.GepStatusRegister(reg)` (StackOps.cs:551). **Ruled out** by code
inspection:

  - `EmitContext.GepStatusRegister` (EmitContext.cs:313) routes through
    `Slots` (the `AllocaSlotProvider`) when set.
  - `BlockFunctionBuilder` enables the alloca provider for any CPU
    with `GprWidthBits <= 16` (BlockFunctionBuilder.cs:155-175), which
    covers LR35902 — and registers F as a non-banked status reg.
  - Therefore branch_cc loads F from the alloca shadow, which receives
    per-instruction updates inline and gets promoted to pure SSA by
    mem2reg. The "stale memory F" failure mode cannot happen.

## What remains (Option A from Gemini: per-instruction trace)

The bug must be one of:
  - (a) Some non-control-flow instruction emitter (ALU / mem / stack)
    produces a different result in JIT vs per-instr StepOne for a
    specific operand combination
  - (b) A multi-instruction state interaction (alloca shadow drift,
    PC alloca write side effect, post-store register read)
  - (c) PC update logic — JIT exits with PC=$4E09 (end-of-block) but
    INTERP's StepOne path keeps PC at the natural advance after each
    instruction. If some sequence (PUSH/POP, RET via stack underflow,
    RST coupled with subsequent PC arithmetic) ends with PC=$003A
    in INTERP, JIT's compile-time block walk wouldn't see it.

The most informative next step is **Option A** — per-instruction trace
buffer that records (PC, A, F, BC, DE, HL, SP) after every instruction
on BOTH JIT and INTERP, then diff side-by-side. Implementation outline:

  1. Add a fixed-size ring buffer to `JsonCpu` state: `(ushort pc,
     byte a, f, b, c, d, e, h, l; ushort sp)[64]` plus `byte idx`.
  2. In `JsonCpu.StepOnePerInstr`: after the StepOne call, write
     state to the next slot.
  3. In `BlockFunctionBuilder`: at the end of each per-instruction
     post-block (before branching to the next pre/exit), emit IR
     that writes the same fields to the same buffer.
  4. In `GbFuzzer` on divergence: print both buffers side-by-side.

This is a ~150 LoC focused diagnostic that can be gated behind an env
var so it doesn't affect production block-JIT.

## Update — second divergence pattern found (seed=42, iter 79)

Re-running the GB fuzzer after Phase 30.18p/q (GBA R15 fixes) on
seed=42 still surfaces 2 divergences. The second one is more
diagnosable:

```
iter 79/seed 74172009: divergence at block #1, pc=0x0150
JIT  POST: PC=0x015D  (= 0x0150 + 13)
INT  POST: PC=0xDBC9
cart bytes @ pc=0x0150..+32:
  07 1F 1E 1E 64 2E 19 69  35 FB C3 C9 DB ...
```

Expected decode of bytes 0x0150..0x015C (13 bytes, 9 instructions):

| PC  | Byte(s)  | Mnemonic       | Len |
|-----|----------|----------------|-----|
| 150 | 07       | RLCA           | 1   |
| 151 | 1F       | RRA            | 1   |
| 152 | 1E 1E    | LD E, $1E      | 2   |
| 154 | 64       | LD H, H        | 1   |
| 155 | 2E 19    | LD L, $19      | 2   |
| 157 | 69       | LD L, C        | 1   |
| 158 | 35       | DEC (HL)       | 1   |
| 159 | FB       | EI             | 1   |
| **15A** | **C3 C9 DB** | **JP $DBC9** | **3** |

`JP nn` has `writes_pc: "always"`, so BlockDetector SHOULD end the
block at the JP. Expected: 9 instructions, JIT exits at JP with
PC=$DBC9. INTERP also exits at JP with PC=$DBC9. **No divergence**.

But `APR_GB_TRACE_BLOCKLEN=1` shows at least one block at $0150
ran with `detected=13 actual=13 pcWritten=0`. Two readings:

  - (a) 13 INSTRUCTIONS at $0150 = each byte treated as a 1-byte
    instruction (no multi-byte handling). Would suggest the
    LengthOracle returned 1 for 0xC3 (it doesn't — explicitly
    returns 3) or the spec decoder treated `C3 C9 DB` as 3 separate
    instructions.
  - (b) 13 INSTRUCTIONS over more bytes via cross-jump-follow into
    the target region (`JP $DBC9` followed → target instructions
    counted). The fuzzer sets `APR_NO_CROSS_JUMP_FOLLOW=1` to gate
    this off, but it's worth confirming the env var actually takes
    effect at the right time.

Open question: is `[BLOCKLEN] detected=13 actual=13 pcWritten=0` from
iter 79 specifically (vs some other iteration's block at $0150)? The
fuzzer doesn't currently print iter context to the BLOCKLEN trace.

## Update (Phase 30.18r/s) — iter 79 bug RESOLVED

`APR_GB_IR_DUMP=ADDR` env-gate added (sequence-numbered files so
multi-iter compiles don't overwrite). Inspecting iter 79's IR for the
$0150 block revealed the actual root cause:

```
i8_exec:                                  ; JP $DBC9
  store i16 -9271, ptr %pc_local          ; JP wrote $DBC9
  store i8 1, ptr %pc_written_ptr         ; PcWritten=1
  call set_ime_fn(i8 1)                   ; EI's deferred body
  sub cycles by 16
  store i16 349, ptr %pc_local            ; ← SYNC CLOBBERED PC = $015D
  store i8 1, ptr %pc_written_ptr         ; PcWritten=1 again
```

The SyncEmitter (from EI's deferred body, injected after JP's own
steps by DeferLowering) unconditionally wrote `bi.Pc + length`
($015D) to PC, overwriting JP's $DBC9. Fix: skip the PC overwrite
when `ctx.PcWriteEmittedInCurrentInstruction` is true. Also made
Branch/Call/Ret use WriteReg.MarkPcWritten so they set that flag.
Commit `8d376da`.

## Status — iter 78 bug STILL OPEN

After Phase 30.18s the GB fuzzer is down from 2 → 1 divergence at
seed=42. The remaining one is iter 78 at $4DF5 with random ROM.

IR-dump-driven analysis (iter 78 block at $4DF5):
  - 18 instructions, no `writes_pc: always` boundary
  - JR cc at instr[6] with C=0 (after CP at instr[3]) → NOT taken
  - Block runs linearly to PC=$4E09

Both JIT and INTERP end with R8 state showing H=$4D (= old L value
before LD L,A at instr[1]) and E=$4D — BUT no instruction in the
list writes H or E with that value.

Gemini hypothesised an 8-bit register setter shift-vs-mask bug
(`HL = (HL << 8) | new_L` instead of `(HL & 0xFF00) | new_L`).
Inspected the LD-r-r emit IR (Lr35902WriteR8Emitter) — IT'S CORRECT.
Each ddd iteration does `select(cmp, raw, prev)`, only writes when
cmp=true, otherwise preserves. The IR for i1 (LD L,A) shows H's
load+select(false, ...)+store-back path, leaving H unchanged.

So the bug is NOT in the WriteR8 emitter as Gemini guessed. The
H corruption to $4D must come from somewhere else. Hypotheses to
investigate next session:
  - Spec has an instruction whose steps incorrectly write H/E
    (audit all step lists for unintended `lr35902_write_r8` to ddd=4
    or `write_reg_pair_named` to HL/DE with stale value)
  - The bus.Tick(N) or memory_write extern is corrupting CPU state
    (PUSH ops modify SP+memory; LD (HL),A writes; if any of these
    have a wild pointer they could overwrite the GPR slots)
  - The alloca shadow drain (DrainShadowsToState at block exit) has
    a register-index mismatch that writes the wrong slot

Diagnostic next step: APR_GB_FORCE_BUDGET=1 + iter 78 single-step.
If H stays $01 with budget=1 (forces effectively 1-instr blocks)
but ends $4D with normal budget, bug is multi-instruction
interaction. If H=$4D with budget=1 too, it's per-instruction.
