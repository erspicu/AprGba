Here is the brutally honest, strictly technical critique of your declarative memory map and dispatch strategy. 

### 1. The String-Tag → C# Handler Routing
**The Verdict:** Under-designed and coupled. Hardcoding a `switch` statement in C# that maps JSON strings to specific component methods defeats the purpose of data-driven specs. You haven’t separated the Machine from the CPU; you’ve just moved the coupling into `NesMemoryBus.cs`. 
**The Fix:** Use a **Handler Registry**. The JSON spec should define a `handler` string. During machine bootup, your components (PPU, APU, Mapper) register their read/write delegates with the bus builder using that exact string.
```csharp
// Boot phase
busBuilder.RegisterHandler("ppu_io", ppu.Read, ppu.Write);
busBuilder.RegisterHandler("wram", ram.Read, ram.Write);

// Bus construction phase matches JSON "handler" to registered delegates
```
This means adding a new side-effect or a 4th CPU system requires *zero* changes to the core bus routing code. 

### 2. `mirror_mask` Semantics
**The Verdict:** Half-baked and mathematically brittle. `(addr & mirror_mask) | start` relies on coincidental bitwise alignment of your start addresses. It will break the moment you have a region starting at `0x1200` that mirrors every `0x0100` bytes.
**The Fix:** Apply masks to the **offset**, not the absolute address. 
```json
"mirror_period": "0x0800" // or mask: "0x07FF"
```
```csharp
// Implementation
int offset = (addr - r.Start) & r.MirrorMask; 
// or: int offset = (addr - r.Start) % r.MirrorPeriod;
return handler(offset); // Handlers should receive offsets, not absolute addresses!
```
Passing the *offset* to the handler (e.g., passing `0-7` to the PPU instead of `0x2000-0x2007`) simplifies the component logic immensely. The component shouldn't care where it is mapped in the address space.

### 3. Tile-The-Whole-Space Assumption (Gaps)
**The Verdict:** Tiling cleanly is an 8-bit luxury. ARM and m68k will laugh at you. Gaps are standard, expected, and necessary.
**The Fix:** Your `if (addr < r.Start) break;` logic works for handling gaps *if* the array is sorted, but it forces "open bus" to return `0`. On many systems, open bus returns the last value on the data lines, or triggers a CPU exception (e.g., ARM Data Abort). 
*   **Validator:** Do NOT complain about gaps.
*   **Spec:** Add a machine-level `"unmapped_behavior": "zero" | "ignore" | "fault" | "last_bus_value"`.
*   **Code:** If `addr` falls in a gap, route it to an `UnmappedHandler` configured by the spec.

### 4. Performance Scaling (The 7% Drop)
**The Verdict:** A linear array scan inside a tight inner interpreter loop is a classic performance killer. The 7% drop isn't from the work being done, it's from the bounds checks and pipeline stalls on the `r.End` branches. It will absolutely tank on a GBA (10+ regions) or ARM.
**The Fix:** Use a **Page Table** (Flat Lookup Array) for the C# fallback, and JIT-emit binary searches (or inline page tables) for LLVM.
For a 16-bit address space (NES), create an array of 64 or 256 handler structs. 
```csharp
// 16-bit space, 1KB pages = 64 elements. 
// Startup time: ~0.01ms to populate.
// Runtime lookup: O(1)
ref var page = ref _pageTable[addr >> 10];
return page.Handler(addr); 
```
For 32-bit (ARM), use a 2-level page table (e.g., top 8 bits point to a sub-table). The memory overhead is trivial (a few KB), and it returns your interpreter to $O(1)$ dispatch time, immediately reclaiming that 7% performance loss.

### 5. The `fastmem_eligible` Flag
**The Verdict:** Leaky abstraction. `fastmem` is a JIT optimization strategy, not a hardware specification. The JSON is dictating compiler optimizations. 
**The Fix:** The spec should only declare hardware facts: `"type": "ram"`. 
The JIT framework should query the Bus at compilation time:
```csharp
if (bus.TryGetHostPointer(addr, out IntPtr hostPtr, out int length)) {
    // LLVM Emitter generates an inline GEP-store
} else {
    // LLVM Emitter generates a callout to the C# Bus
}
```
This decouples the JIT from the JSON. If the region is backed by a pinned C# `byte[]` and has no complex read/write side effects, `TryGetHostPointer` succeeds. 

### 6. Side-Effect Ordering (`side_effects[0]` for routing)
**The Verdict:** Hidden semantic rules ("the first element in this array is magically the primary routing key") are a classic source of tech debt. 
**The Fix:** Be explicit. Separate the *handler* from the *side-effects*.
```json
{
  "name": "cart_prg",
  "handler": "mapper",
  "snooped_by": ["other_system"],
  "is_pure": false
}
```
If an address write needs to go to two places, the Bus's registration system (from Point 1) should compose a multicast delegate, or the primary handler should trigger the side effect. 

### 7. General Sanity Check (Over/Under-design)

**Remove (Over-design):** 
*   `forces_end_of_block`: The hardware doesn't know what a JIT basic block is. Replace this with `"volatile": true` or `"is_pure": false`. The CPU's JIT compiler should decide that a volatile memory access terminates a block.

**Add (Under-design - Critical for CPUs 3 and 4):**
*   **Access Widths:** NES is 8-bit, but GBA/ARM components care deeply about access widths. A 16-bit write to 8-bit SRAM on GBA ignores the top byte. A 8-bit write to GBA VRAM writes the same byte twice (mirrored) or is ignored depending on the exact address. Your region spec *must* support `"allowed_widths": [8, 16, 32]` and `"width_mismatch_behavior"`.
*   **Permissions:** Add `"readable": true` and `"writable": false`. A write to ROM shouldn't require a dummy C# handler; the bus should reject it via the spec.
*   **Wait States / Cycles:** If you want accurate timing later, memory regions need cycle penalties. GBA GamePak ROM is notoriously slow (e.g., 4 wait states for sequential, 2 for non-sequential). Add a `"wait_states": { "seq": 1, "nonseq": 1 }` object for future-proofing.

### Summary Strategy for N4:
1. **Change JSON schema:** swap `side_effects[0]` to `"handler": "str"`, add explicit `mask` and access permissions, remove JIT-specific flags.
2. **Refactor Bus Builder:** Parse JSON, map `"handler": "ppu"` to `Action/Func` via a runtime registry. 
3. **Optimize Dispatch:** Throw away the 4-element struct array loop. Build a 64-element array (1KB pages) that maps `addr >> 10` directly to the registered delegate. (This guarantees you will beat your legacy MIPS benchmark).
