Here is a review of your proposed JSON spec inheritance feature for AprCpu, structured exactly to address your four topics.

### 1. Design Concept Review

Your approach is a **"Data-Driven Overlay/Mixin"** model. It sits uniquely on the spectrum compared to industry standard approaches:

*   **MAME** uses C++ OOP inheritance. It’s great for sharing I/O and state, but ISA execution often degrades into macro-heavy C++ copy-paste or massive `switch` statements peppered with `if (has_feature_X)`. 
*   **QEMU (TCG)** uses single, monolithic target directories (e.g., `target/i386`). It handles generations via runtime feature flags (e.g., checking `CPUID_EXT_SSE41` inside the translation loop). It has no concept of declarative inheritance.
*   **Ghidra (SLEIGH)** uses a preprocessor (`@include`) and constructor overrides. It is powerful but famously difficult to debug because include chains become "spaghetti," and resolving which `.sinc` file defined a specific bit-pattern requires deep mental stack-tracing.

**Where AprCpu fits:** You are effectively building something akin to **JSON Patch (RFC 6902)** or Kubernetes `kustomize`, but tailored for ISAs. Because the merge happens entirely at load-time, your JIT and decoder remain blissfully unaware of the hierarchy, keeping runtime performance optimal. 

**Pitfalls to avoid:**
*   **The "God Base Class" Trap:** Do not put 8086-specific quirks into an abstract base if the 286 removes them. 
*   **Feature Flags vs. Inheritance:** If the *only* difference between two CPUs is the presence of an FPU (e.g., 8086 vs 8086+8087), using inheritance creates combinatorial explosion. 
*   **DO:** Treat your JSON inheritance strictly as a *build/load-time AST macro* system, not runtime OOP.
*   **DON'T:** Fall into deep inheritance trees. Keep it shallow (Max depth 3 or 4).

### 2. JSON Spec Format

Your proposed schema is clean, but the selector design and override granularity need adjustment for x86.

**Granularity (Partial vs. Full Replace):**
*   **DO support partial field merges.** In the x86 family, instruction encodings almost never change between generations, but **cycle counts change drastically** (e.g., 8086 `MUL` takes ~118 cycles; 286 `MUL` takes ~21). If you require full replacements, you will copy-paste massive blocks of IR-emitter metadata just to change a `"cycles": 21` field.
*   Adopt JSON Merge Patch (RFC 7386) semantics for the `replace_with` block. If a key is provided, it overwrites; if omitted, it inherits.

**The Selector:**
*   **DON'T use `"opcode_byte"` as your primary selector.** x86 is a variable-length nightmare. Many instructions share the same primary opcode byte and use the ModR/M `reg` field as an opcode extension (e.g., `0x80` is shared by `ADD`, `OR`, `ADC`, `SBB`, `AND`, `SUB`, `XOR`, `CMP`).
*   **DO use a stable, unique ID string** for every instruction (e.g., `"id": "ADD_rm8_imm8"`). Use this ID as the dictionary key for inheritance overrides. 

**Validation of `from`:**
*   **DO make it a hard validation.** If `from: "i8086"` is specified, the loader *must* crash if `i8086` did not declare that instruction. If it is just documentation, it will drift, and you will end up with silent no-ops where an override failed to apply because of a typo in the selector.

**Refined Schema Suggestion:**
```json
{
  "architecture": { "id": "i80186", "extends": "i8086" },
  "instruction_set_diff": {
    "overrides": {
      "MUL_rm16": {
        "cycles": { "base": 35, "mem_penalty": 4 } 
        // Emits merged instruction: keeps 8086 encoding/IR, updates cycles
      }
    },
    "removals": [ "POP_CS_0F" ],
    "additions": {
      "PUSHA_60": { "opcode": ["0x60"], "ir_emitter": "emit_pusha" }
    }
  }
}
```

### 3. Implementation Recommendations

**(a) Debug visibility:** 
**DO** include `_inherited_from` and `_overridden_by` metadata in the merged, in-memory JSON DOM. When an emulator bug occurs, running `aprcpu --dump-merged i80286` to see exactly *why* a specific instruction has a certain IR emitter is invaluable. Strip this metadata only at the final JIT phase.

**(b) Cyclic inheritance and Multiple Parents:**
**DON'T** allow multi-parent inheritance (`extends: ["i8086", "i8087"]`). The diamond problem in JSON merges is impossible to resolve cleanly. 
**DO** hard-fail on cyclic inheritance. 
*Alternative:* If you need to mix in FPU or SSE instructions without creating combinatorial branches (e.g., `386+387`, `486`, `486SX`), implement a `traits` or `includes` array that only allows *additive* overlays (no overrides permitted from traits).

**(c) Schema evolution:**
**DON'T** create a separate `inheritance_protocol_version`. Since inheritance is resolved at load-time to produce a finalized spec, any change to how merging works fundamentally changes the resulting ISA data. Tie it to the main `spec_version`.

**(d) Validation Strictness:**
**DO** fail fast and hard. If a child spec tries to remove an instruction that doesn't exist in the parent, throw a load-time exception. Strictness is the only way to prevent a 3000-line JSON file from silently rotting over 5 years of maintenance.

### 4. Intel Family Split Points

Your rules (R1 to R4) are excellent heuristics. Here is how they apply to your specific uncertainties:

**(a) MMX: Aliasing vs Shape Change**
*   **Verdict:** Break the chain (New chain for MMX).
*   *Reasoning:* While MMX registers physically alias the x87 FPU stack, logically and architecturally, they introduce a massive state-management difference. Using MMX requires the `EMMS` instruction to clear FPU tag bits. The data types shift from 80-bit floats to packed integers. Attempting to shoehorn this via JSON overrides into an older CPU spec will pollute the FPU definitions. 

**(b) 80386 protected mode vs 80286**
*   **Verdict:** Break the chain (Fresh chain for 386).
*   *Reasoning:* The 386 completely redefines memory addressing. It introduces the SIB byte, 32-bit offsets, a totally new descriptor table format, paging (CR0-CR4), and changes the default address/operand sizes. Even if real-mode 386 looks like a 286, your decoder logic for fetching operands will be completely rewritten. Inheriting 286 here is a trap.

**(c) 8086 ↔ 8088**
*   **Verdict:** Sibling specs extending an abstract base.
*   *Reasoning:* The ISA is 100% identical. The only difference is the 8-bit external bus on the 8088, which alters cycle timing (memory accesses take longer) and the prefetch queue size (4 bytes vs 6 bytes). 
*   *Action:* Create `spec/x86-16/_base_808x.json`. Have `i8086.json` and `i8088.json` extend it, applying only `instruction_set_diff.overrides` to patch their specific cycle timings.

**(d) Pentium → Pentium Pro (P6)**
*   **Verdict:** Do NOT break the chain. `PPro` extends `Pentium`.
*   *Reasoning:* Microarchitectural changes (Out-of-Order execution, register renaming) are completely invisible to an ISA-level JIT emulator. At the declarative JSON level, P6 just adds `CMOVcc`, `FCMOV`, `SYSENTER`, and a few others. The register shape, word size, and prefixes remain identical. 

**Summary of recommended Intel split points:**
1.  **x86-16 Chain:** `_base_808x` -> `8086` & `8088`. Then `8086` -> `80186` -> `80286`.
2.  **x86-32 Base Chain:** `80386` -> `80486` -> `Pentium`. (New chain due to 32-bit addressing, SIB, paging).
3.  **x86-MMX Chain:** `Pentium_MMX` -> `Pentium_II`. (New chain due to MMX state/tag semantics).
4.  **x86-SSE Chain:** `Pentium_III` -> `Pentium_4`. (New chain due to XMM registers and fundamentally new execution units).
5.  **x86-64 Chain:** `AMD64`. (New chain due to REX prefixes, unified general-purpose register expansion to R8-R15, and RIP-relative addressing).
