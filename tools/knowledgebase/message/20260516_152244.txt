RESPONSE
========================================================================
Your hypothesis is absolutely brilliant, entirely correct, and you have stumbled upon a classic rite-of-passage bug in PC emulator development. 

The exact behavior you are seeing—an infinite loop of `SEEK`, `SENSE INT`, and `READ DATA` on LBA 0—is the signature footprint of a "stuck" Disk Change line.

Here are the detailed answers to your questions:

### 1. Does port 0x3F7 bit 7 = DSKCHG returning 1 explain the symptom? What is the correct default?
**Yes, 100%.** 

When FreeDOS processes output (even `stdout`), it routinely checks file handles and device status. If it queries the floppy drive and sees the Disk Change bit set, it assumes the user swapped the disk. To prevent corrupting a potentially new disk, it immediately invalidates its FAT/directory cache and forces a read of the Boot Sector (LBA 0) to check the BIOS Parameter Block (BPB) and Volume Serial Number. 

Because your emulator always returns `0xFF` for unmapped ports, Bit 7 (0x80) is always `1`. Therefore:
1. DOS writes a char.
2. DOS checks drive status -> Sees DSKCHG.
3. DOS reads LBA 0.
4. DOS expects the BIOS/FDC `SEEK` command to have cleared the DSKCHG line.
5. DOS writes the next char, checks status -> Sees DSKCHG *again* (because you return 0xFF).
6. Rinse and repeat.

**The correct default:** For an emulator that is not currently simulating disk swapping, reads from `0x3F7` should return **`0x00`** (or **`0x7F`**). This leaves Bit 7 as `0`, indicating "No Disk Change."

*Note on XT vs AT:* The original IBM PC/XT (8272 FDC) didn't actually have a Disk Change line! It was introduced with the PC AT (1.2MB drives). However, FreeDOS and modern BIOSes will blindly read `0x3F7` anyway. If they see Bit 7 set, they act on it.

### 2. What other registers/behaviors of port 0x3F7 do you need to model?
For a basic PC emulator running DOS, you only strictly need to care about **Bit 7**. 

Here is exactly what `0x3F7` is on standard AT hardware:
*   **READ - Digital Input Register (DIR):**
    *   `Bit 7`: DSKCHG (1 = Disk Changed, 0 = No Change).
    *   `Bits 6-0`: On real hardware, these are usually undriven and float high. Therefore, returning **`0x7F`** is the most physically accurate response for a disk that hasn't been swapped.
*   **WRITE - Configuration Control Register (CCR):**
    *   `Bits 1-0`: Data Rate Select (00 = 500 Kbps, 01 = 300 Kbps, 10 = 250 Kbps, 11 = 1 Mbps).
    *   *You usually don't need to emulate this* unless you are booting a protected mode OS like Linux or OS/2 that strictly enforces FDC timing/data rates. DOS/BIOS will write to it, but you can safely ignore the writes in a basic emulator.

**If you want to emulate disk swapping later:**
You will need to make Bit 7 "sticky." Set it to `1` when the user changes the disk image via your emulator UI. Clear it to `0` when the FDC receives a `SEEK` or `RECALIBRATE` command *and* a step pulse is actually issued to the drive head.

### 3. Is MSR (0x3F4) polled at ~465/sec independent of the command stream?
**No, it is strictly tied to the command stream.** Fixing `0x3F7` will completely cure this.

Here is why your trace showed 465 reads of `0x3F4` and 135 reads of `0x3F5`:
To talk to the FDC Data Register (`0x3F5`), the CPU **must** first read the Main Status Register (`0x3F4`) and check Bit 7 (RQM - Request for Master) to ensure the FDC is ready to accept or yield a byte. 

Look at your command loop: `SEEK` (3 bytes) + `SENSE INT` (3 bytes) + `READ DATA` (16 bytes). That's roughly 22 bytes exchanged per cycle. 
At ~6 cycles per second (based on your timestamp delta of ~160ms between reads), DOS is transferring ~135 bytes per second. This matches your `0x3F5` (Data) read count *perfectly*.

Because your emulator runs at ~500K inst/sec, when the BIOS wants to read a byte from the FDC, it enters a tiny spin-loop:
```assembly
wait_fdc:
    in al, dx      ; Read 0x3F4 (MSR)
    test al, 80h   ; Is RQM bit set?
    jz wait_fdc    ; Spin if not ready
```
The ~465 reads of `0x3F4` simply means the BIOS loops about 3 to 4 times on average before your FDC emulator says "I'm ready" and allows the data transfer on `0x3F5`. 

Once you fix the DSKCHG line on `0x3F7`, DOS will realize the disk hasn't changed. It will stop issuing the `SEEK/READ` commands, the BIOS will stop spinning on the MSR, and the internal `ver` command string will dump instantly to the screen. 

**Summary of your fix:**
Map a read handler for `0x3F7` that simply returns `0x7F`. Watch the magic happen.
