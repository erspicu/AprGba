### FINDING 1: The "Invisible" Text (Attribute 0x00)

Your deduction is spot on. If the characters are pushing old text up, the BIOS `INT 10h` Teletype (`AH=0Eh`) and Scroll (`AH=06h`) routines are successfully executing on the framebuffer you are rendering. The text is there, but the attribute byte is rendering it invisible.

**1. Could there be a "video mode" mismatch where INT 10h writes with attribute 0 (black-on-black)?**
Yes, absolutely. In text mode, the BIOS Teletype function (`INT 10h, AH=0Eh`) **does not set the attribute byte**. It simply writes the ASCII character to the even address and skips the odd (attribute) address, leaving whatever color was already there. 
However, when the screen hits the bottom and needs to scroll, the BIOS calls Scroll Up (`INT 10h, AH=06h`). This function *requires* the caller to pass a "fill attribute" in the `BH` register for the newly created blank line at the bottom. If `BH` is `0x00`, the new line is filled with black-on-black spaces. Subsequent Teletype writes will put characters on that line, but since Teletype preserves the existing attribute, the characters remain black-on-black!

**2. What changes after we reach A:\> that flips the attribute to 0x00?**
When `COMMAND.COM` (FreeCom) loads, it often executes a `CLS` (Clear Screen). To know what color to clear the screen with, DOS calls `INT 10h, AH=08h` (Read Character and Attribute at Cursor). 
If the cursor happens to be resting on a cell that initialized with `0x00`, DOS will use `0x00` to clear the entire screen. From that point on, every scrolled line and every typed character inherits the `0x00` attribute. 

**3. Could FreeDOS CON/FreeCom write to BDA[0x49] or BDA[0x65]?**
- `BDA[0x49]` (Current Video Mode): Unlikely to be overwritten by DOS, but DOS *reads* it to decide how to talk to the BIOS.
- `BDA[0x49]` is Mode 7 for MDA. Mode 3 for CGA.
- `BDA[0x65]` (Current Video State/CRT Mode register): DOS doesn't usually mess with this, but ANSI.SYS equivalents might.

**4. Is the BDA properly populated for MDA?**
This is the most likely root cause. The original PC/XT BIOS (`pcxtbios.bin`) **does not auto-detect video cards**. It determines the video mode by reading the motherboard DIP switches via an I/O port (Port `0x62` on the XT, or the 8255 PPI chip on the PC). 
*If your emulator does not emulate the XT DIP switch port returning the correct bits for MDA, the BIOS POST will assume CGA (Mode 3).*
If the BIOS initialized for CGA:
1. It set `BDA[0x49] = 3` (CGA).
2. It set the active page segment in the BDA to `0xB800`.
3. The bootloader might have bypassed the BIOS and written directly to `0xB0000`, which is why you saw the boot text.
4. When DOS loads, it strictly uses BIOS `INT 10h`. If the BIOS thinks it's in CGA mode, the scrolling and cursor math might be calculating offsets incorrectly, or writing to `0xB8000` while your auto-detect is still locked onto `0xB0000`, OR the BIOS scroll routine is defaulting to an attribute of `0x00` because the BDA state is confused.

**How to fix/debug Finding 1:**
*   **Dump the framebuffer memory:** When the screen goes invisible, pause the emulator and look at `0xB0000`. You will likely see `44 00 49 00 52 00` (D, attr 0, I, attr 0, R, attr 0). This confirms the 0x00 attribute bug.
*   **Check the BDA:** Look at `RAM[0x0449]`. If it is `0x03`, the BIOS thinks you have a CGA. If it is `0x07`, the BIOS correctly knows you have an MDA.
*   **Hack fix:** In your `X86CgaRenderer`, temporarily change `Palette[0]` from Black to Dark Gray. If the invisible text suddenly appears as gray text, you have 100% confirmed the issue is the attribute byte being `0x00`.

### FINDING 2: Keyboard Shift States

Your emulator is currently acting like a macro-pad that only sends raw keystrokes, completely bypassing the PC keyboard protocol's concept of modifier keys.

**5. What does the real PC XT BIOS INT 9 ISR do?**
The XT keyboard uses "Set 1" scancodes. It sends a scancode when a key is pressed (Make code), and the same scancode + `0x80` when the key is released (Break code).
When the `INT 9h` ISR sees `0x2A` (Left Shift Make), it sets Bit 1 of `BDA[0x17]` (Keyboard Shift Flags). It doesn't put anything in the keyboard buffer. 
When it sees `0x05` ('4'), it checks `BDA[0x17]`. Because the Shift bit is set, it looks up the shifted value ('$') and puts *that* in the circular keyboard buffer at `BDA[0x1E]`.
When it sees `0xAA` (`0x2A + 0x80`, Left Shift Break), it clears Bit 1 of `BDA[0x17]`.
Because you only inject `0x05`, `BDA[0x17]` is always 0, so you always get '4'.

**6. Can you just poke BDA[0x17] directly from the host?**
*Technically yes.* You could intercept `Shift+4` on the host, manually set `RAM[0x0417] |= 0x02`, inject `0x05`, and then clear `RAM[0x0417] &= ~0x02`. 
*Should you?* No. It's prone to race conditions (if the emulator executes `INT 9h` at the wrong microsecond, or if the BIOS itself is modifying `0x17` due to a Caps Lock toggle). It also won't work for software that reads raw scancodes from port `0x60` directly (like many DOS games).

**7. What's the right approach in an emulator?**
**Option (b)** is the universal standard for PC emulation. You should map Host `KeyDown` to XT Make codes, and Host `KeyUp` to XT Break codes. The BIOS will naturally maintain the shift states exactly as a real PC would.

Here is the standard way to implement Option (b) in WinForms:

```csharp
// In your MainForm:
protected override void OnKeyDown(KeyEventArgs e)
{
    byte scanCode = MapKeyToScancode(e.KeyCode);
    if (scanCode != 0) 
    {
        // Inject MAKE code to Port 0x60, trigger IRQ1
        cpu.Keyboard.InjectScancode(scanCode); 
    }
    e.Handled = true;
}

protected override void OnKeyUp(KeyEventArgs e)
{
    byte scanCode = MapKeyToScancode(e.KeyCode);
    if (scanCode != 0) 
    {
        // Inject BREAK code (Make + 0x80)
        cpu.Keyboard.InjectScancode((byte)(scanCode | 0x80)); 
    }
    e.Handled = true;
}

private byte MapKeyToScancode(Keys key)
{
    switch (key)
    {
        case Keys.D4: return 0x05;
        case Keys.ShiftKey: 
        case Keys.LShiftKey: return 0x2A; // Left Shift Make
        case Keys.RShiftKey: return 0x36; // Right Shift Make
        case Keys.Enter: return 0x1C;
        // ... map all other standard keys ...
        default: return 0;
    }
}
```
*Note:* In WinForms, holding a key down relies on Windows KeyRepeat, which fires `KeyDown` repeatedly. Real XT keyboards also repeat the Make code when held. So WinForms' default behavior maps perfectly to XT behavior!

### Next Steps Summary
1. Change your WinForms keyboard handling to track `KeyDown`/`KeyUp` and send Make/Break scancodes. This will instantly fix the Shift, Ctrl, and Alt keys.
2. Pause the emulator when text goes invisible and check `RAM[0x0449]` to see if the BIOS thinks it's in MDA (7) or CGA (3) mode.
3. Check the memory at `0xB0000` to confirm if the attribute bytes are `0x00`. 
4. If it is `0x00`, investigate how your emulator handles the XT Motherboard DIP Switches (usually read via `IN AL, 62h` on an XT). If the BIOS reads all 0s from your un-emulated port, it defaults to a mode that doesn't match your MDA expectations.
