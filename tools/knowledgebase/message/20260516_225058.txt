This is fantastic debugging. You’ve hit exactly the kind of deep architectural quirk that makes writing PC emulators both maddening and rewarding. 

What you are seeing is a classic **"mixed-responsibility scrolling bug"** caused by how DOS and BIOS interact. The short answer is: **FreeDOS is likely calling an explicit Scroll Up (INT 10h, AH=06h) and passing `BH=0` because a *different* BIOS function lied to FreeDOS about what the current screen attribute is.**

Here is the breakdown of your questions and the grand theory of what is happening.

### The Grand Unifying Theory: Why rows 15-24 are invisible
Standard DOS (including FreeCom/FreeDOS) sends output to the `CON` device driver via INT 21h. The `CON` driver relies on the BIOS (INT 10h). 
1. When printing characters, DOS uses **AH=0Eh** (Teletype). Standard AH=0Eh writes the character but **preserves the existing attribute** in VRAM.
2. When the cursor hits the bottom of the screen and a Line Feed is issued, DOS does *not* always rely on the BIOS AH=0Eh implicit scroll (which you patched). Instead, the DOS `CON` driver often explicitly scrolls the screen by calling **INT 10h, AH=06h (Scroll Up)**.
3. When DOS calls AH=06h, it must pass the blanking attribute in `BH`. How does DOS know what attribute to use? It asks the BIOS by calling **INT 10h, AH=08h (Read Character and Attribute at Cursor)**.

**The Suspected Bug:** I strongly suspect `pcxtbios` has a bug in **AH=08h**. When in Mode 7 (MDA), it's probably reading from the CGA segment (`0xB800`) instead of the MDA segment (`0xB000`). Because your emulator's `0xB800` segment is empty/zeroed, AH=08h returns `AH=00h` (attribute 0). 
FreeDOS thinks the current attribute is 0. It calls AH=06h with `BH=0`. The BIOS scrolls the screen and fills the new bottom row with `attr=0`. DOS then prints characters using AH=0Eh, which *preserves* the `attr=0`, making the text invisible!

Here are the answers to your specific questions based on this theory:

---

### 1. Does FreeCom pass BH=0 explicitly?
Not intentionally. COMMAND.COM uses standard streams. But the underlying FreeDOS kernel `CON` driver calculates the fill attribute by dynamically reading the screen using INT 10h AH=08h. If the BIOS returns 0, DOS passes 0 to AH=06h. DOS trusts the BIOS.

### 2. Is the BDA[0x4C] = 0x4000 (Regen Size) the underlying bug?
**Yes, it is a glaring bug in `pcxtbios`, but it is likely a secondary symptom of the root cause.** 
You are absolutely correct: Mode 7 is 80x25 text (4000 bytes) and requires a 4KB (0x1000) regen buffer. The `4000h` is meant for Mode 6 (Graphics, 16KB). Grouping Mode 6 and 7 together in that BIOS table is flat-out wrong.

*However*, since MDA only has one page (Page 0), the VRAM offset calculation `(PageNum * RegenSize)` evaluates to `(0 * 0x4000) = 0`. So it probably still points to the correct start of VRAM (`0xB000:0000`). This bug *will* cause problems if software tries to write to Page 1, but it's likely not the direct cause of your `attr=0` bug on Page 0.

### 3. Direct VRAM writes by COMMAND.COM?
Unlikely. Standard `dir` relies purely on DOS standard output so that redirection (`dir > file.txt`) works. Unless you have an ANSI driver loaded (like `NANSI.SYS` or `FDAPM`), FreeDOS is exclusively relying on INT 10h. 

### 4. Is the "N rows visible, the rest invisible" an emulator bug pattern?
Yes, it is the textbook signature of **"Teletype Scroll vs. Window Scroll mismatch."** 
When you booted, the initial text was output before the kernel fully took over, triggering your patched BIOS AH=0Eh implicit scroll (`BH=0x07`). It worked perfectly. But once `dir` executed, it dumped multiple lines rapidly, engaging the DOS kernel's explicit AH=06h scroller, which used the broken `BH=0` attribute. 

### 5 & 6. FreeCom `dir` and Volume Label output paths
`dir` builds the volume string and the file listing using the exact same standard output (C `printf` or DOS INT 21h AH=40h). 

**Why is Row 14 partially visible (48 chars good, 32 bad)?**
This perfectly matches the theory!
*   The screen scrolled (clearing the new row 14 to `0x0020` spaces).
*   DOS printed "Volume Serial Number is 858E-3E5F". 
*   Wait, if AH=0Eh preserves the 0 attribute, why are those 48 chars visible? Because FreeCom might output the Volume Label using a slightly different DOS function, or an ANSI sequence, that *does* force the attribute to 0x07 for the text itself. But it doesn't print spaces to the end of the line. Therefore, the last 32 cells remain untouched—as the `attr=0` spaces left behind by the bad scroll.

### 7. Recommended Next Steps

You do not need an HLE dispatcher yet. You are incredibly close. Do this:

1.  **Trace INT 10h calls in your emulator.** 
    Put a hook on your CPU emulator right before it executes the `INT 10h` software interrupt. Log `AH`. 
    *   Watch for `AH=08h` (Read Char/Attr). Look at what it returns in `AX`. If `AH` (attribute) comes back `00`, you've found the bug.
    *   Watch for `AH=06h` (Scroll Up). Look at what is passed in `BH`. If it is `00`, the scroll is your culprit.
2.  **Audit `pcxtbios` AH=08h and AH=06h code.**
    Look at the assembly for `pcxtbios`'s AH=08h function. I bet you will see it hardcoding the `0xB800` segment, or misreading the CRT base port from BDA[0x63] (which should be 0x3B4 for MDA, but is 0x3D4 for CGA). 
3.  **Fix the BIOS `regen_len` table.**
    Since you are already patching `pcxtbios`, fix that table offset F000:F0A4 so Mode 7 uses `1000h`. 
4.  **Patch AH=06h in the BIOS (Temporary Fix).**
    If you confirm FreeDOS is calling AH=06h with `BH=0`, you can temporarily binary-patch the BIOS AH=06h handler: check if `BH=0` and mode=7, and if so, force `BH=0x07`. This will immediately prove the theory and get your emulator's console working while you fix the underlying AH=08h read bug.
