Based on the excellent diagnostic details you’ve provided, here is the analysis of your JIT vs. Interpreter divergence.

### Q1 — Top 3 Hypotheses for the Divergence Root Cause
**1. Self-Modifying Code (SMC) / JIT Cache Invalidation Failure** *(Most Likely)*
*Rationale:* FreeDOS’s boot sector at `0:7C00` relocates itself by copying its code to `1FE0:0000` via `REP MOVSW`, then does a far jump to the new segment. If your block-JIT caches translated LLVM blocks based on physical addresses, and your DMA or CPU memory writes don't invalidate the JIT cache for the `1FE0` page, the CPU will jump to `1FE0:XXXX` and execute the stale `00 00` translation that was cached when that memory was empty. 
*(Note: Your memory watch likely showed "NO writes" because either your DMA or your JIT-emitted memory store instructions bypass the C# MMU wrapper where the watch is implemented).*

**2. Block-Boundary Device Ticking / Timing Desync**
*Rationale:* The interpreter likely ticks the PIT/FDC/DMA after every single instruction, whereas the JIT ticks them at block exits. This massive timing difference means a BIOS loop polling the FDC might timeout prematurely in the JIT, or DMA transfers might not finish before the CPU jumps to the loaded code, causing FreeDOS to jump into uninitialized memory.

**3. Miscompiled Segmented Control Flow (Far JMP/CALL/RET)**
*Rationale:* FreeDOS makes heavy use of Far Calls and Returns to transition between segments during early boot. If your JIT's `PcWritten` logic fails to properly update the base `CS` or miscalculates the physical address for the next block fetch after a far control-flow instruction, execution will resume at a garbage offset (like `9D0F`).

---

### Q2 — Is IRET mishandling the stack?
**No. Your IRET and stack are almost certainly working perfectly.**
*Rationale:* The CS:IP progression you observed (`9D0F, 9E8F, A00F, A18F...`) is the "smoking gun." Notice that the difference between these offsets is exactly **`0x180` bytes**. 
In x86, `00 00` decodes to `ADD [BX+SI], AL`, which is a 2-byte instruction. `0x180` bytes equals exactly **192 instructions**. 
Your JIT CPU has already crashed into a zero-filled memory region and is executing a "zero-sled". Your LLVM block builder likely has a maximum block size limit (or hits a page boundary) at 192 instructions. 
The timeline is: 
1. CPU executes 192 instructions of `00 00`.
2. Block exits.
3. Dispatcher ticks devices; IRQ 0 is pending.
4. Dispatcher pushes the *correct* current CS:IP onto the stack and handles INT 8.
5. IRET pops the CS:IP and returns to the zero-sled.
6. CPU executes the next 192 instructions of `00 00`. 
The bug happened *before* the interrupt; the interrupt is just faithfully taking snapshots of a runaway CPU.

---

### Q3 — Best Diagnostic Strategy
**Recommendation: Wire up `LockstepDiff` at the Block Exit boundary, but temporarily disable hardware interrupts (PIT/FDC) to ensure deterministic execution.**
*Rationale:* Because the JIT and Interpreter group instructions differently, hardware interrupts will fire at different architectural instruction counts, causing a false divergence in `LockstepDiff`. 
1. Hardcode a bypass to disable PIT IRQ 0 and FDC interrupts, forcing the BIOS/FreeDOS to rely on CPU polling or fail deterministically. 
2. Wire `LockstepDiff` so that the JIT executes *one block*, and the Interpreter executes *N instructions* until its CS:IP matches the JIT's exit CS:IP.
3. Assert that `AX..DI`, `FLAGS`, `DS, ES, SS` match exactly. 

This will immediately pinpoint the exact basic block where the JIT miscalculates a register, drops a memory write (revealing an MMU bypass), or branches to the wrong target, cutting through the noise of millions of executed instructions.
