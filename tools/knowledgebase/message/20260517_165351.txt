Here is a second opinion on your divergence. Your analysis is sharp, and you are right to suspect block-specific state shadowing. 

Here is the breakdown of what is likely happening based on the emitted IR, the Game Boy flag layout, and the `A=$4D, F=$80` footprint.

### 1. The Emitter Snippet is Mathematically Sound
First, your generic ALU IR generation for `ADD/ADC` is correct. 
* `loSum > 0xF` correctly computes the Game Boy Half-Carry (`H`).
* `result32 > 0xFF` correctly computes Carry (`C`).
* `n = 0` correctly clears the Subtract flag. 
* *As you noted:* Since `Pre F=$00`, `C` is 0. Passing `F.C` as `cZ` for `ADD` instead of a constant 0 is a bug, but it is **dormant** here because `C` was already 0.

Because the snippet is mathematically sound, and because it works in `INTERP` (and likely per-instr mode), the issue is almost certainly in **how the JIT routes data into/out of `aZ`, `sZ`, and the resulting assignments** via allocas.

### 2. The "Stale L Shadow" Hypothesis (Why JIT A=$4D)
The most glaring clue in your JIT output is **`A = $4D`**. 
Notice that `$4D` is the **exact pre-block value of `L`**.

If you trace the first two instructions of the block:
1. `0x85` (ADD A, L): Expected to compute `A = $9C` (from $4F + $4D).
2. `0x6F` (LD L, A): Expected to copy that `$9C` into `L`.

If your block-JIT has an alloca shadowing bug where **`LD` instructions fail to update the local alloca**, `L` will be left stale. 
* What if `LD L, A` bypasses the local `alloca` and writes directly to the CPU context memory pointer?
* What if you have separate allocas for 16-bit `HL` and 8-bit `L` that `mem2reg` doesn't sync? 

If `L`'s alloca is never updated by `0x6F`, it remains `$4D`. If later in those 18 instructions an instruction moves `L` into `A` (e.g., `LD A, L` or an ALU operation that writes to A), it will read the stale alloca and inject `$4D` back into `A`. 

### 3. The "Eventually Zero" Pattern (Why JIT F=$80)
In the Game Boy, the flag register is laid out as `Z N H C` (bits 7, 6, 5, 4).
`F = $80` perfectly translates to **`Z=1, N=0, H=0, C=0`**. 

This is the exact footprint of an operation resulting in zero that *also* clears the subtract flag (`N=0`). 
* It **cannot** be `CP` (0xFE), because `CP` unconditionally sets `N=1` (which would yield `F=$C0` or similar). 
* It **cannot** be `SUB`, because that also sets `N=1`.
* It **can** be a bitwise operation like `XOR`, `OR` (which clear N, H, C), or an `ADD` that wrapped exactly to 0. 

If `A` was populated with the stale `$4D`, and a later instruction happened to be `XOR L` (where the stale `L` is also `$4D`), it would compute `$4D ^ $4D = 0`. This sets `Z=1, N=0, H=0, C=0` (F=$80). 

### Actionable Bisecting Steps
To hunt this down, look for these specific well-known JIT bug classes in your `alloca + mem2reg` Phase 7 setup:

1. **Dump the Pre-Optimized LLVM IR**: Look at the block right before `mem2reg` runs. Trace the `store` instructions for `0x6F (LD L, A)`. I highly suspect you will find that it is either storing to the wrong pointer (e.g., the backing context pointer instead of the local alloca) or it was completely optimized away (Dead Store Elimination) due to pointer casting.
2. **Check 16-bit vs 8-bit Type Punning**: LLVM's `mem2reg` pass **will completely ignore** allocas if they are accessed via pointer casts. If you allocate a 16-bit `i16` for `AF` or `HL`, but then cast to `i8*` to write to `A` or `L`, LLVM drops SSA promotion for those registers. You end up reading stale stack garbage or the initial prologue values.
3. **Verify the Epilogue (Block Exit)**: Ensure your block exit doesn't accidentally write the initial, unmodified `alloca` captures back into the CPU Context, overwriting the valid work done in memory.
