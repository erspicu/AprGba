Here is a fresh perspective on your investigation. You are running into a classic cognitive trap with Block-JIT debugging, but your hypotheses are extremely sharp. 

### Why the bug seems to "move"
You noted: *"Cap=N at $4DF5 for any N <= 17: divergence keeps moving to next block"*. 

The divergence isn't actually moving. The bisection tool is splitting your 18-instruction block into two chunks:
1. **Chunk 1 (Capped):** Instructions `1` to `N`.
2. **Chunk 2 (Uncapped):** Instructions `N+1` to `18`.

When you cap at `N`, Chunk 1 runs and perfectly matches INTERP. But the bisection tool then lets Chunk 2 run as a single **uncapped** block. Because the actual buggy instruction lives somewhere inside Chunk 2, the block executes all the way to the end (Instruction 18), and the divergence only manifests at the final exit PC ($4E09). 

The tool successfully proved that **instructions 1 through 17 can execute perfectly**, which means the actual desync is isolated to **Instruction 18**. But because Instruction 18 is part of the uncapped remainder, it looks like the bug is "running away" to the next block boundary.

### Evaluating your Hypotheses
Your hypotheses are completely coherent with the symptoms (`JIT PC=$4E09` vs `INTERP PC=$003A`):
* **H1 (Decoder Desync):** If the block-detector missed a length correctly, JIT might be linearly compiling trailing garbage (e.g., parsing an opcode as `55 LD D,L`), while INTERP correctly parses a `JR C` or `RST 38h` and branches.
* **H3 (Missing PcWritten flag):** This is an **incredibly common** JIT bug. If your `branch_cc` emitter correctly writes `cpu->PC = target` but forgets to set the IR's `PcWritten=1` flag, the JIT loop won't bail out. It will just fetch the next linear instruction, compile it, and eventually overwrite the `cpu->PC` at the end of the block with `$4E09`. The branch is effectively erased.
* **Hidden Hypothesis (Mid-block Interrupt):** Since this is a fuzzer, `IME` might be 1. If an interrupt fires during the block, INTERP takes it immediately (jumping to an ISR, eventually landing at `$003A`). JIT, however, defers the interrupt check until block exit, executing all 18 instructions linearly.

### The Most Efficient Next Step
You should absolutely go with **Option (A): Add a per-instruction trace-buffer.** 

Since block-bisection leaves you staring at a multi-instruction "black box" (the uncapped remainder), you need X-ray vision into the JIT's execution. 

**Why Option A is the silver bullet:**
1. If **H3** is true, the trace will show JIT's PC failing to update after a `JR` instruction, falling right through while INTERP's PC jumps.
2. If **H1** is true, the trace will show JIT executing a completely different mnemonic/opcode than INTERP at step `K`.
3. If it's a **mid-block interrupt**, the trace will show INTERP's PC magically changing to an interrupt vector (`$0040`, `$0048`, etc.) without a branch instruction, while JIT blindly continues.

### How to implement Option (A) quickly (Don't over-engineer it):
1. Add a simple fixed array to your CPU state struct: `struct { uint16_t pc, a, f, bc, de, hl; } trace[64];` and an `uint8_t trace_idx`.
2. In your JIT's instruction-compile loop, right after emitting the logic for an instruction, emit a quick routine that stores the current shadowed state into `trace[trace_idx++]`.
3. Run the fuzzer. When the block ends and triggers the divergence, loop through the `trace` array and print it side-by-side with INTERP's per-instruction step data. 

**Skip (B) and (C) for now.** (B) assumes H3 is the only answer and sends you hunting in LLVM IR, which wastes time if the issue is actually H1 or an interrupt. (C) is just a more complicated version of (A). 

Implement the trace buffer. The side-by-side diff will literally point an arrow at the exact instruction and root cause within minutes.
