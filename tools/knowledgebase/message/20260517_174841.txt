internal sealed class Branch : IMicroOpEmitter
{
    public string OpName { get; }
    private readonly BranchKind _kind;
    public Branch(string opName, BranchKind kind) { OpName = opName; _kind = kind; }

    public void Emit(EmitContext ctx, MicroOpStep step)
    {
        var targetName = step.Raw.GetProperty("target").GetString()!;
        var target = ctx.Resolve(targetName);
        var (pcPtr, pcType) = StackOps.LocateProgramCounter(ctx);

        if (_kind == BranchKind.Link) { /* ARM only, not used for LR35902 JP */ }

        var coerced = StackOps.CoerceToType(ctx, target, pcType, "branch_target");
        ctx.Builder.BuildStore(coerced, pcPtr);
        var flagSlot = ctx.Layout.GepPcWritten(ctx.Builder, ctx.StatePtr);
        ctx.Builder.BuildStore(LLVMValueRef.CreateConstInt(LLVMTypeRef.Int8, 1, false), flagSlot);
    }
}

private sealed class Call : IMicroOpEmitter
{
    public string OpName => "call";
    public void Emit(EmitContext ctx, MicroOpStep step)
    {
        var (pcPtr, pcType) = LocateProgramCounter(ctx);
        var (_, _, wordBytes) = LocateStackPointer(ctx);
        LLVMValueRef curPc;
        if (ctx.PipelinePcConstant is uint pipelineValue)
            curPc = LLVMValueRef.CreateConstInt(pcType, pipelineValue, false);
        else
            curPc = ctx.Builder.BuildLoad2(pcType, pcPtr, "call_pc_cur");
        PushWord(ctx, curPc, wordBytes, "call");
        var target = ResolveCallTarget(ctx, step, pcType);
        var coerced = CoerceToType(ctx, target, pcType, "call_target");
        ctx.Builder.BuildStore(coerced, pcPtr);
        var flagSlot = ctx.Layout.GepPcWritten(ctx.Builder, ctx.StatePtr);
        ctx.Builder.BuildStore(LLVMValueRef.CreateConstInt(LLVMTypeRef.Int8, 1, false), flagSlot);
    }
}

Based on the code snippets and your bisection observations, here is a concrete analysis of what is happening.

### (Q1) & (Q3) Do you spot the bug in the code / `branch_cc` emitter?

Yes. The bug is highly likely in how **not-taken conditional branches** interact with the block's natural exit. 

In Q3, you mentioned that `branch_cc` does this:
```llvm
select(pred, target, curPc) -> stored to PC
select(pred, 1, oldFlag) -> stored to PcWritten
```
If the branch evaluates to **NOT TAKEN** (`pred == 0`):
1. It stores `curPc` (the address of the branch instruction itself) to the `PC` in memory.
2. It stores `oldFlag` (which is `0`) to `PcWritten`.

Because `PcWritten == 0`, `postBB[i]` routes execution to `budgetCheckBB[i]` and then `advanceBB[i]`, allowing the JIT block to continue executing the subsequent fallthrough instructions. This is perfectly correct *during* the block.

**The Bug:** Look at `advanceBB[i]` in **CODE 4**:
```csharp
advanceBB[i]: br preBB[i+1] (or blockExit if last)
```
If this not-taken branch happens to be the **last** instruction in the block (e.g., instruction 18), `advanceBB` branches directly to `blockExit`. It **never stores `nextInstrPc` to the memory PC**. 
As a result, the JIT exits the block leaving the `PC` in memory exactly as it was last modified. Because the not-taken `branch_cc` forcefully wrote `curPc` into memory, the JIT will exit the block with the `PC` rolled back to the address of the branch instruction, instead of the end of the block!

*(Note: In your specific POST JIT state, `PC=$4E09` implies that a `budgetExitBB` actually triggered and saved you by overwriting `PC` with `nextInstrPc`. However, this exact pattern is a ticking time bomb for block exits).*

### (Q2) Does the bisection reading match? 

Your reading of the bisection is partially on track, but you missed a crucial implication of your own findings.

You observed:
* `Cap=1`: Block 1 matches. Next block (Block 2, uncapped) diverges.
* `Cap=17`: Block 1 matches. Next block (Block 2, uncapped) diverges.

If the first 17 instructions *perfectly match* between the JIT and Interpreter when capped to 17, it definitively proves that **instructions 1 through 17 executed perfectly**. Neither a buggy branch nor a corrupted state happened in the first 17 steps.

The divergence **strictly happens at instruction 18**. When you cap the block, you force an early exit before instruction 18. The bug occurs because instruction 18 fails *only when it is executed as part of a block's tail, or when an uncapped block naturally exhausts*.

### (Q4) Why did A and F diverge so wildly?

If instruction 18 was a conditional branch that the JIT evaluated as **not taken**, but the Interpreter evaluated as **taken**, the Interpreter jumps to a new location (e.g., `$003A`) and executes instructions there (modifying `A` and `F`). The JIT falls through to `$4E09` and does not modify `A` and `F` further.

**Why would they evaluate conditions differently?**
This points to an **SSA / Register Caching bug**. In block JITs, registers like `F` are often held in local LLVM SSA variables during the block and flushed to memory at the end. 
If your `branch_cc` emitter reads the `F` flag directly from `ctx.StatePtr` (memory) instead of the active SSA cache, it will read the **stale `F` flag** from the start of the block! 
* In the JIT, instruction 18 reads the stale memory `F=$00`, evaluates `Z=0` (Not Taken), and falls through to `$4E09`.
* At `blockExit`, the JIT correctly flushes the active SSA `F` to memory (resulting in your observed POST JIT `F=$80`).
* The interpreter correctly evaluated the updated `F=$80`, saw `Z=1` (Taken), jumped to the target, and executed code that resulted in `A=$60, F=$20`.

This also perfectly explains your sub-theory (a) where `LD A, L` seemingly read an old value of `L`. If an instruction reads from the memory struct instead of the SSA pipeline, it will fetch the `PRE` block state.

### (Q5) Could it be the cycle-budget exit?

Another highly probable cause for this exact footprint (JIT PC=`$4E09`, Interp PC=`$003A`): **Delayed Interrupt Polling**.

`$003A` is exactly one instruction deep into the `$0038` `RST 38H` (Timer/FF) interrupt vector.
* **Interpreter:** Polls for interrupts before *every* instruction. If an interrupt became pending at instruction 17, the Interpreter pushes the PC, jumps to `$0038`, executes one instruction, and ends at `$003A` (changing `A` and `F` in the handler).
* **JIT:** Evaluates 18 instructions as a single, atomic basic block. It won't check for interrupts until the block hits `budgetExitBB` or finishes. Therefore, the JIT ignores the interrupt, blindly executes the 18th fallthrough instruction, and exits normally at `$4E09` without jumping.

When you cap the block to 1 (`Cap=1`), the JIT exits and polls interrupts after every instruction, flawlessly keeping sync with the interpreter. When uncapped, the JIT delays the interrupt by up to 17 instructions, causing immediate divergence.

### Summary of what to fix:
1. **Interrupt Polling:** Ensure the JIT forces a `budgetExitBB` (e.g. `cyclesLeft = 0`) if a hardware interrupt becomes pending mid-block, OR ensure the verifier accounts for block-boundary interrupt polling.
2. **Not-Taken Branch PC Leak:** In your `branch_cc` emitter, change `select(pred, target, curPc) -> stored to PC` to just bypass the store entirely if not taken, OR ensure `advanceBB[last]` strictly stores `nextInstrPc` before hitting `blockExit`.
3. **Register Stale Reads:** Verify that `branch_cc` queries the `F` register from your SSA/pipeline cache, not via a memory load from `ctx.StatePtr`.
